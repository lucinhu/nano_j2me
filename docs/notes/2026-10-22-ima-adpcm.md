## 诊断

把原 JAR 解包后，资源文件 `11`、`11.1`、`11.2` 都以 `RIFF....WAVE` 开头，`fmt `
块的 `wFormatTag` 是 **0x11 —— Microsoft IMA ADPCM**，不是 PCM 的 1：

- 8 kHz、单声道、4 bit、`block align` 256；
- `data` 块分别 2304 / 5120 / 5632 字节（整块数不同）；
- 每块前 4 字节是头：s16 首样本 + 8 位 step index + 保留字节；其后每字节装两个
  4 bit nibble，先低后高。

`src/midp/nj_lib_media.c` 的 `wav_parse()` 原先只接受 `fmt == 1` 的 PCM，遇到
0x11 直接返回 0，于是 `createPlayer()` 走“无解码器”分支抛出上面的异常。

## 修改（`src/midp/nj_lib_media.c`）

- `wav_info` 增加 `nj_u4 bytes; int adpcm; int block;`：带上 `data` 块的真实长度、
  IMA 标志和 `blockAlign`（原实现按 `bits/8` 算帧数，对 4 bit 不成立）。
- 新增 IMA 解码器和两张标准表：
  - `static const int ima_index_table[16]`、`static const int ima_step_table[89]`；
  - `static int ima_decode(int nibble, int *step_index, int *predictor)`；
  - `static nj_u4 wav_ima_decode(const nj_u1 *src, nj_u4 len, int channels,
    int block, nj_u1 *dst, nj_u4 dst_cap)`：逐块读每声道头，按 4 字节单元展开
    nibble（立体声时左右声道按 4 字节单元交替），输出 little-endian s16。
- `wav_parse()` 接受 `fmt==0x11 && (chan==1||2) && bits==4 && rate>0 &&
  block_align >= 4*chan+4`，帧数
  `(data_len/block) * (2*(block-4*chan)/chan + 1)`（半块尾部按填充丢弃）。
- `createPlayer()` 的成功路径里，ADPCM 文件先整段解码成 16-bit PCM 再交给原来的
  PCM 路径（`wi.bits=16`、`F_P_DATA` 换成解码后的数组）；解码不到样本时仍抛
  `MediaException("this WAV file holds no PCM samples")`，而不是把一段静音交给
  port。解码量按文件大小一次分配，之后 pump / port hook / duration 计算都与
  PCM 文件完全相同。

## 边界

- 只实现 IMA ADPCM（`wavFormatTag 0x11`）的 4-bit 单/双声道；其它 ADPCM 变体
  （如 MS ADPCM 0x02、Yamaha 0x20）仍会被拒绝并报 `not a PCM WAV`。
- 没有做“听感”对比：headless port 记录的是解码后的 PCM 帧数/时长，SDL port 交给
  系统音频设备；波形正确性由 fixture 的确定性时长与帧数断言保证，未做频谱比对。
- 文明5 的回合推进（AP 驱动）与其余 29 JAR 的覆盖状态不因本修复改变，见
  [回合按钮与指针通道](2026-10-22-civ5-turn.md) 与
  [语料清单](2026-10-17-download-corpus.md)。
