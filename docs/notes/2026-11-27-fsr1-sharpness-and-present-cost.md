# FSR1 锐度灵敏度与 4×/8× 真实窗口呈现耗时

本轮（第 5 轮）先回答两个问题：放大链路里唯一还能调、且用户可选的旋钮
（RCAS 锐度 `sharp`）到底值不值得按倍率单独调；以及 4×/8× 高清镜像的
呈现耗时究竟花在哪一步。两问都指向同一个结论：**空间放大链路已经饱和，
继续调参没有可迁移的收益**，剩下的都是结构性改动。

## 一、方法

* 探针 `.local-tools/debug-runs/fsr-round5/probe5.c`：EGL surfaceless 环境下
  直接调用生产代码的 `nj_gles2_present`（mode 5，FSR1 + RCAS），把一帧逻辑
  画面依次放大到各个目标尺寸，写出 `<tag>_<W>x<H>.rgba`。锐度通过
  `nj_gles2_present_set_sharp` 设置（运行时可调，范围 0.05–1.0）。
* 对照使用确定性的 Doom3 原生渲染：
  `.local-tools/debug-runs/fsr-quality-round3-3d/doom-8x/dump-frames/00240.ppm`
  （1920×2560，原生 8× 无 FSR 渲染）。参考图 = 该图到目标尺寸的**精确分数面积
  缩小**（逐轴累积覆盖权重，等价于积分图面积采样），与呈现端 mode 5 的缩小语义一致。
* 两种源：
  * **完美源**：8× 原生渲染精确面积缩小到 240×320。用来隔离放大核本身的误差。
  * **真实源**：`.local-tools/debug-runs/fsr-quality-round3-3d/doom-1x/dump-frames/00240.ppm`
    （游戏实际输出的 240×320 原生 1× 渲染）。用户看到的就是这一路。
* 指标：RGB MAE（0–255）与 8×8 块亮度 SSIM，均对参考图计算。
* 呈现耗时：SDL 真实窗口回放，`SDL_VIDEODRIVER=offscreen` + GLES2 + mode 5，
  同一镜像分别投到 551×751 与 960×1280 两个窗口，40 次呈现取中位数/p95。

## 二、锐度扫描

完美源（MAE / SSIM）：

| 目标 | sharp 0.2 | 0.4 | 0.6 | 0.87055056（发布默认） | 1.0 |
| --- | --- | --- | --- | --- | --- |
| 480×640（2×） | 2.251 / .9789 | **2.242 / .9792** | 2.260 / .9785 | 2.383 / .9733 | 2.548 / .9666 |
| 720×960（3×） | 2.330 / .9734 | **2.325 / .9737** | 2.328 / .9737 | 2.382 / .9718 | 2.485 / .9679 |
| 960×1280（4×） | 2.389 / .9605 | 2.385 / .9605 | **2.385 / .9606** | 2.435 / .9584 | 2.526 / .9546 |
| 1440×1920（6×） | 2.413 / .9623 | **2.411 / .9624** | 2.410 / .9623 | 2.440 / .9608 | 2.503 / .9579 |
| 1920×2560（8×） | 2.466 / .9481 | 2.465 / .9481 | **2.463 / .9480** | 2.486 / .9463 | 2.539 / .9434 |

真实源（同一参考）：

| 目标 | sharp 0.05 | 0.2 | 0.4 | 0.6 | 0.87055056 | 1.0 |
| --- | --- | --- | --- | --- | --- | --- |
| 480×640 | 3.895 / .9587 | **3.891 / .9590** | 3.933 / .9574 | 3.991 / .9534 | 4.128 / .9460 | 4.295 / .9376 |
| 960×1280 | **3.980 / .9458** | 3.980 / .9458 | 3.982 / .9457 | 3.998 / .9450 | 4.067 / .9412 | 4.133 / .9372 |
| 1920×2560 | **4.008 / .9409** | 4.008 / .9409 | 4.008 / .9409 | 4.009 / .9408 | 4.029 / .9393 | 4.067 / .9369 |

读法：

1. **误差对锐度是单调的**：锐度越低，MAE/SSIM 越好，0.05–0.2 时趋近“无 RCAS”
   的基线。参考图是面积平均（本身就模糊），而 RCAS 是按感知锐度设计的，
   任何对比度增强都会让面积误差变大。这是**度量语义的偏差**，不是实现缺陷，
   所以不能用这两个指标去“优化”出更低的锐度默认值。
2. **锐度的影响随倍率迅速衰减**：2× 时从默认 0.87 降到 0.05 可把 MAE
   从 4.128 降到 3.895（−5.6%），而 8× 只从 4.029 降到 4.008（−0.5%）。
   高倍率下每个纹素已经铺得很开，RCAS 的对比度限幅几乎不起作用。
3. 因此**“按倍率给不同锐度”没有依据**（各倍率最优值平摊在 0.2–0.6 且差异
   在噪声量级），发布默认仍是 AMD 参考值 `exp2(-0.2)=0.87055056`；想要更柔或
   更锐由用户在「FSR1 锐度」里调，桌面用 `NJ_GL_PRESENT_SHARP`。
   这与第 2 轮的立方核 A 扫描（14 个取值只带来 0–1.9% 收益）是同一结论。

## 三、4×/8× 真实窗口呈现耗时

同一帧、同一窗口尺寸，只改 HD 镜像倍率（median / p95，毫秒）：

| 源（HD 镜像） | → 551×751 窗口 | → 960×1280 窗口 |
| --- | --- | --- |
| 4× 960×1280（3.7 MB） | 0.754 / 0.942 | 1.742 / 2.135 |
| 8× 1920×2560（15 MB） | 2.715 / 3.133 | 4.268 / 4.714 |

同一窗口下 8× 比 4× 多约 **1.96 ms**，对应多上传 15 MB，约 7.6 GB/s 的有效
带宽——耗时几乎全部是“把 CPU 端 HD 镜像上传成 GL 纹理”，而不是 GPU 的
双三次重建或 RCAS 采样。镜像越大，`glTexSubImage2D` 越贵；GPU 滤波和
窗口合成可以忽略。

这条数据的意义是给结构性方案定规模：要让 4×–8× 的呈现成本降下来，必须让
HD 镜像**留在 GPU**（3D 直接渲染到 FBO / 共享纹理，present 只做采样），或者
不再把整块镜像每帧推上 GPU。它是多步改动（涉及 GL 三角路径、软件光栅路径、
2D 合成层的失效判定与回退），不适合以单个小步提交，留作后续轮次的结构性项。

## 四、结论

* 放大/缩小、锐度、立方核参数都已被量化，空间链路没有安全的增量收益；
  `docs/notes/2026-11-27-fsr-scale-matrix.md` 的默认值是当前最优选择。
* 剩余可推进的方向只有两类：**HD 镜像驻留 GPU** 的呈现结构，以及
  **4×–8× 时域链**（FSR2@3× 后再空间放大 + 2D 覆盖合成）。两者都需要
  跨模块改造，应先做单轮设计再落地。
* 本轮同时修掉了 libretro 保存状态的看门狗误杀，见
  [libretro 保存超时](2026-11-27-libretro-state-timeout.md)。
