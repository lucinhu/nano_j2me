# JSR 184 fuzz round 2 (round-5): animation, skinned/morphing meshes, mipmaps, Loader

Date: 2026-11-02. Branch `r5-bugs` (based on main `331686f`).

This note records the second seeded fuzz round over the M3G (JSR 184)
implementation, the real bugs it found, the fixes, the saved-state
compatibility they required, and the evidence needed to re-run every claim.
It is a companion to `2026-11-02-m3g-fuzz.md` (round 4, light/submesh index
bounds). Nothing here changes valid-input rendering.

## 2. Finding A: `AnimationTrack` did not extend `Object3D`

*Symptom.* Duplicating a keyframe track built by `Loader.load` aborted with
`java/lang/NoSuchMethodError: javax/microedition/m3g/AnimationTrack does not
implement javax/microedition/m3g/Object3D.duplicate`. `animate()`,
`setUserID()`/`getUserID()` and casts of a track to `Object3D` failed the same
way: the virtualization lookup runs from the receiver class up its superclass
chain, and the builtin class table registered `AnimationTrack` as extending
`java/lang/Object` instead of `Object3D`.

*JSR 184 says* `public class AnimationTrack extends Object3D` (the generated
API stubs agree; all other 24 M3G classes matched).

*Fix.* `src/midp/nj_lib_m3g.c`: the class-table entry for `NJ_C_ATRACK` now
names `NJ_C_O3D` as its superclass, with a comment. Inherited Object3D methods
(and `instanceof`) now work; `duplicate()` returns an `AnimationTrack`.

*Regression test.* `tests/test_m3g.c:test_object3d_subclass_api` (7 checks):
hierarchy is `AnimationTrack -> Object3D`, `setUserID`/`getUserID` round-trip,
`animate(0)` runs, `duplicate()` is non-null, its class is `AnimationTrack`, and
the copy keeps the track's target property. Pre-fix evidence:
`animationtrack/prefix-test_m3g.log` (874 checks, 7 failures); post-fix:
`animationtrack/postfix-test_m3g.log` (874/0).

### 2.1 Saved-state compatibility (src/core/nj_save.c)

The saved-state format records each builtin class's `instance_size` and an ABI
hash, and `nj_vm_load` refused any state whose class shapes differ. Correcting
the superclass grows `AnimationTrack`'s instance by the 32 bytes of
`Object3D`'s fields (64 -> 96), so **every state written before the fix** -
including the original Minecraft world state - was refused at resume. This is
the same constraint that kept `FileConnection.isOpen()` out of the round-2
fix.

Because the state format and its ABI check are pinned, a **bounded migration**
was added in `nj_vm_load` rather than bumping the format:

* Accepted only when the runtime class **grew** (`have instance_size >
  saved`), and only when `field_count`, `method_count` and `is_array` are
  identical. A shrink or any other difference is still refused.
* The ABI hash for that class is recomputed as the legacy shape
  (`class_abi_hash_legacy`): instance_size and every non-static field offset
  are reduced by the growth, so the hash proves the declaration is otherwise
  unchanged (static offsets are absolute and unchanged). Every other class is
  hashed strictly as before.
* After the arena image is read, the object-table walk counts objects per
  class. If the state actually holds an instance of a migrated class, load is
  refused with
  `saved state holds an instance of javax/microedition/m3g/AnimationTrack
  (legacy instance_size=64, now 96)`. That is what makes the migration safe:
  with zero instances no old field offset is ever dereferenced, and with an
  instance the old offsets would be wrong, so refusing is the only correct
  answer.
* The mechanism is generic - any builtin class whose superclass (or field set)
  is corrected later and grows by exactly its inherited fields can migrate -
  but it deliberately does not accept anything else: no shrinking, no
  field/method additions, no layout changes that are not a pure growth, and no
  saved instances of a migrated class.
* Debug output is gated by `NJ_SAVE_DEBUG=1` (the success line is
  `class javax/microedition/m3g/AnimationTrack: migrating legacy shape
  (saved inst=64, have inst=96)`).

Re-runnable evidence: `tools/m3g_fuzz2_state_evidence.sh
<new-nj2me> <legacy-nj2me> [<legacy-world-state> <minecraft-jar>]` checks all
three paths and never touches the given state (it copies it): legacy instance
state refused, new-format state round-trips, and - when a real legacy world
state is supplied - the class migrates and the MIDlet resumes. Logs:
`animationtrack/legacy-instance/{save-legacy2,load-legacy-instance,load-new}.log`,
`animationtrack/mc-sanity-with-fix-and-migration.log`,
`mc-r5/mc-release.log`, `mc-asan/mc-asan.log`.

## 3. Finding B: `Background` crop overflow in the clear path

*Symptom.* UBSan:
`src/midp/nj_lib_m3g.c:4102:13: runtime error: signed integer overflow:
2147483647 + 1073741823 cannot be represented in type 'int'` in
`m3g_background_image` (`clear(Background)` -> `m3g_clear`). Reached with
`Background.setCrop(Integer.MAX_VALUE, Integer.MAX_VALUE, Integer.MAX_VALUE,
Integer.MAX_VALUE)` and a viewport. Crop and viewport are Java ints, and the
sampler did `int sy = cy + (int)(((double)y - vy + 0.5) * ch / vh)` (same for
`sx`): the cast and the addition both overflow for legal input.

*Fix.* Compute `sy`/`sx` in `double`, refuse values outside
`(-2147483649.0, 2147483648.0)` (covers the float-to-int undefined conversion,
NaN and `vh == 0`), add the crop origin in `nj_s8`, wrap in 64-bit for repeat
mode, bounds-check in 64-bit, then narrow to int. Valid pixels are unchanged.

*Regression test.* `tests/test_m3g.c:test_background_crop_extremes` (3 checks):
`clear(Background)` with an `Integer.MAX_VALUE` crop and with an
`Integer.MIN_VALUE` crop must not fault, and the fixtures must allocate.
Pre-fix: `prefix-bg-crop.log` (`... 2147483647 + 67108863 ...`, UBSan abort,
1 failure); post-fix: `postfix2-test_m3g.log` (877/0 ASan+UBSan) and
`postfix2-test_m3g-release.log` (877/0 Release).

## 4. Finding C: implicit-strip index overflow in `jr_strip`/`jr_draw`

*Symptom.* UBSan:
`src/midp/nj_lib_m3g.c:12736:15: runtime error: signed integer overflow:
2147483647 + 1 cannot be represented in type 'int'` in `jr_strip` <-
`jr_draw` <- `m3g_world_draw`. For a triangle strip with no index array
(`idx == NULL`), the renderer computes `first + i` in int; a loader-built
`TriangleStripArray` can carry `_nj_first` near `Integer.MAX_VALUE` (the file
loader stores the field, the constructor range check does not run), so the
addition is undefined behaviour before `jr_vertex()` rejects the vertex.
`jr_draw` accumulated strip lengths into the same int base (`2147483647 + 3`).

*Fix.* Both places use `nj_s8`: `jr_strip` computes the three indices in 64
bits and skips a triangle whose index cannot be an int; `jr_draw` keeps the
running base in 64 bits, bounds it against `ilimit` for indexed strips in
64-bit, and ends the table when a base cannot be an int. Drawing of valid
strips is unchanged.

*Regression test.* `tests/test_m3g.c:test_jr_strip_implicit_extreme_first`
(1 check, forked child like the other renderer probes): populates a
TriangleStripArray the way the loader can (`_nj_ib_data` null, one 3-vertex
strip, `_nj_first = 0x7FFFFFFF`) and renders it; UBSan aborts the child before
the fix. Pre-fix: `prefix-jr-strip.log` (`... 2147483647 + 1 ...`, 878 checks /
1 failure); post-fix: `postfix3-test_m3g.log` (878/0 ASan+UBSan) and
`postfix3-test_m3g-release.log` (878/0 Release).

## 5. Investigated, no bug found

* `KeyframeSequence` times/keys, SLERP/SQUAD component rules, `AnimationTrack`
  properties and `AnimationController` extremes: range-checked; only the
  hierarchy above was wrong.
* SkinnedMesh/MorphingMesh constructors and bone rosters: array lengths,
  weights and vertex scopes are validated; 400-op waves with degenerate
  weights/skeletons produced only specified exceptions.
* Texture2D/Image2D mip levels and format/pixel mismatches: level chain and
  pixel coverage are validated before sampling (also checked in round 4).
* Loader: the synthetic-container (structured and random payload) waves,
  truncations and every offset boundary produced only the documented
  `IOException`s and the reserved/too-many-objects checks; no crash.
* Note the sanitizer blind spot: Java arrays live inside the VM's `nj_heap`
  arena, so ASan cannot see an over-read inside the arena. Findings above are
  UBSan reports and API-level failures (plus the earlier round's real SEGV),
  and every fix has a pre-fix log.
