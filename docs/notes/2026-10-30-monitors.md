# 2026-10-30 - `synchronized` now excludes: real Java monitors

## What was wrong

`monitorenter` was bookkeeping.  `nj_vm_monitor_enter()` wrote the object into
the current frame's `monitor` field and returned; nothing ever blocked.
`Object.wait()` found its wait set by scanning the small thread table, and
`notify()` woke threads, so the wait/notify *tests* passed - but two threads
could run the same `synchronized` block at the same time.

The comment that justified it was wrong in one word: a cooperatively scheduled
thread is never preempted by a *timer*, but it is preempted at every
instruction-count quantum boundary, and that boundary lands inside critical
sections all the time.

`tests/lockdemo` is the fixture that measures it.  Two threads run the same
`synchronized (LOCK)` block 200 times, yield 40 times *inside* it, and flag any
moment when both are inside at once:

```
$ ./build/nj2me --port headless --heap 8 --size 176x208 --stats \
      tests/fixtures/lockdemo.jar
LOCK counter=400 overlap=true        # before: the race is real
LOCK counter=400 overlap=false       # after
```

## What a Java monitor has to do

1. Entry excludes other threads.  A contending thread parks until the owner
   leaves; a re-entrant entry on the same thread only bumps a count.
2. `Object.wait()` releases the monitor for its whole duration and the thread
   owns it again *before* `wait()` returns.  A notified thread is therefore not
   runnable yet - it may have to wait for the monitor.
3. `notify()`/`notifyAll()` require that the caller owns the monitor.
4. `synchronized` methods own their monitor before the first bytecode runs and
   release it however the frame ends - normal return, `athrow`, or unwind.
5. A monitor left owned by a dead or unwound frame is a leaked lock: every
   waiter parks for ever.

## Design

**No lock word in the object header.**  `include/nj2me/nj_types.h:117` is
`struct nj_object { cls, u, length, size, kind, mark, aflags }`; a header field
would grow every object on devices where the heap is 16 MB.  Instead a thread
owns up to `NJ_MAX_MONITORS` (8) monitors - more than javac emits for real
code - in two parallel arrays on `struct nj_thread`, `monitors[]` and
`mon_depth[]`.  Ownership tests scan `vm->threads[]`, which has at most
`NJ_MAX_THREADS` entries.

**Blocking is a pc rewind, not a rebuilt stack.**  `nj_vm_monitor_enter()`
returns 1 for "blocked": the thread state becomes `NJ_THREAD_BLOCKED`, its
saved pc still points at the objectref-producing instruction pair, and the
interpreter returns `NJ_ERR_YIELD`.  When the wait is ever over, the thread
re-executes the instruction.  This is why the `interp_invoke()` path can block
*inside* a synchronized method call and simply pop the callee frame again - the
arguments are still on the caller's operand stack.

**`wait()` frees the monitor and wakes the right side.**  `nj_vm_monitor_wait()`
removes the monitor from the waiting thread's array (recursion depth saved in
`wait_depth`), then calls `mon_wake_waiters()`, which hands the monitor to a
thread already notified on it, or makes one blocked entrant runnable.  A thread
that is woken is only `wait_ready`; the scheduler calls
`nj_vm_monitor_reacquire()` and the thread runs when it owns the monitor again.
The C-call pump (`src/core/nj_vm.c`) has the same rule for a
`wait(timeout)` inside a `paint()` or a constructor: it reacquires, it does not
resume unlocked.

**The C bridge had to learn about `BLOCKED`.**  A paint invoked from C used to
treat *any* `NJ_ERR_TIMEOUT` other than sleep/wait as a failure.  With real
monitors, `paint()` can block on a monitor held by the title's worker thread,
and NBA篮球2007_10887 printed "paint() on bu failed without raising an
exception (status -5)" once per frame.  The bridge now pumps `BLOCKED` like
`SLEEPING`/`WAITING`, and the scheduler counts a thread woken inside its own C
call as progress instead of declaring "all threads are waiting".

**Roots and snapshots.**  The collector marks `th->monitors[]` - a parked owner
must not have its lock object collected - and snapshot version 3 saves each
thread's monitor list, recursion depths and wait state, so a restored run does
not start with a critical section unowned.

## Behaviour that changed

- `notify()`/`notifyAll()` outside the monitor now throw
  `IllegalMonitorStateException` (the specification requires it).
- A ninth simultaneously held monitor throws `IllegalStateException`; javac
  never emits that (the fixture corpus agrees).
- `Object.wait()` on an object the caller does not own throws
  `IllegalMonitorStateException`.
