# 毁灭战士3: an AMR track inside an MP4, and the class that was missing

## What was wrong

`Manager.createPlayer()` answered 毁灭战士3's every sound with

```
MediaException: this is not a container this runtime knows: cannot parse the media
```

The assets are named `snd/d3theme.amr`, `snd/pistol_shot_02a.amr`,
`snd/pistol_use_01.amr` and `vid/doom.3gp`, and all four are ISO base media
(MP4) files: `file` calls them "ISO Media, MP4 Base Media v1".  Nothing named
`.amr` is required to be an RFC 4867 `#!AMR\n` stream, and a J2ME title that
ships its audio inside the container its 3gp video uses is not unusual.

Two separate faults hid behind one message:

1. The sniffer only recognised an MP4 by the *size byte* of its first box
   (`00 00 00 {0C,18,20}`), which is a guess that holds only for the particular
   box sizes some muxers write.  Doom's `ftyp` is 20 bytes (`00 00 00 14`), so
   the file was reported as "an unrecognised container" and never reached the
   AMR branch at all.
2. Even once recognised as MP4, there was no way to reach the audio: no MP4
   reader existed, and the AMR decoder in `nj_amr.c` only understood the
   `#!AMR\n` concatenation.

## The container, as the real file has it

`d3theme.amr` is 216624 bytes:

| box | offset, length |
| --- | --- |
| `ftyp` | 0, 20 |
| `mdat` | 20, header 8, payload [28, 192060) |
| `moov` | 192060, 24564 |

`moov/trak/mdia/minf/stbl`:

* `stsd` holds exactly one entry, `samr`, 53 bytes = 8-byte box header +
  28-byte AudioSampleEntry + 17-byte `damr`.
* `damr` is 3GPP TS 26.244's shape, 17 bytes total: vendor(4),
  decoder_version(1), mode_set(2), then one reserved bit and seven bits of
  frames per sample.  (`damr[8] & 0x7F`.)
* `stsc` has one entry: `first_chunk = 1`, `samples_per_chunk = 1`,
  `sample_description_index = 1`.
* `stsz` is the constant-size form: `sample_size = 32`, `sample_count = 0x1771`
  = 6001, and no per-sample table.
* `stco` has 6001 offsets: the first is 28, each next is +32, so sample *n* is
  [28 + 32n, 28 + 32(n+1)) and the last one ends exactly at the end of the
  `mdat` payload.

The walk a decoder needs is therefore: find the one `samr` track, then for each
stsc run map samples to chunks, read each chunk's samples out of the chunk
offset, and require every byte to lie inside an `mdat` payload.

## What was added

* `src/midp/nj_amr_mp4.h`, `src/midp/nj_amr_mp4.c` - a bounded, allocating-free
  sample iterator.  It parses `moov`, walks each `trak` down to `stbl`, accepts
  exactly one `samr` track (a second AMR track is refused rather than picking
  one), reads `stsz`/`stsc`/`stco` (or `co64`), and cross-checks them against
  each other: the sample count implied by stsc must equal stsz's, every chunk
  offset must start inside an `mdat`, and every sample is bounds-checked before
  it is returned.  Anything inconsistent, truncated, or ambiguous is refused
  with 0/-1 instead of being guessed at.  3711 bytes of text, no data, no BSS,
  no heap.
* `nj_amr_mp4_frames()` / `nj_amr_mp4_decode()` in `src/midp/nj_amr.c`, with the
  same signatures and PCM shape as `nj_amr_frames()` / `nj_amr_decode()`:
  count frames first, size the Java byte array once, decode straight into it.
  A sample's bytes are walked frame by frame and must agree with `damr`'s
  framesPerSample, so a lying size table stops the track instead of deciding
  how much of the next chunk is read.
* `src/midp/nj_lib_media.c`: the sniffer now recognises `ftyp` by its four
  characters at offset 4 (the old size-byte test stays for files that do not
  spell it); the AMR branch takes both layouts.  An MP4 with no readable AMR
  track is still refused honestly ("this runtime has no MP4 audio decoder")
  rather than turned into a silent Player.

## The second failure, revealed by the first fix

With the track decoding, `Doom.Doom.video()` got past
`Manager.createPlayer()` for its 3gp and then did

```java
vidCtrl = (VideoControl) player.getControl("VideoControl");
```

and the MIDlet died on an **uncaught** `NoClassDefFoundError:
javax/microedition/media/control/VideoControl` - the class did not exist, and
`video()` catches `Exception`, not `Error`.  `VideoControl` is now declared as a
built-in interface (`nj_lib_media.c`, abstract methods, super `Control`).
`getControl()` still returns null for it, which is what MIDP says to do for an
unsupported control; the NPE that follows `initDisplayMode` is caught by the
game's own `catch (Exception)` at pc 73..221 and the intro is skipped.  Games
must not be able to kill the runtime by asking whether it can do video.

## Verification

* Real assets through the new reader - `open == 1`, every frame decoded:

  | asset | bytes | 20 ms frames |
  | --- | --- | --- |
  | `snd/d3theme.amr` | 216624 | 6001 |
  | `snd/pistol_shot_02a.amr` | 1848 | 35 |
  | `snd/pistol_use_01.amr` | 1668 | 30 |
  | `vid/doom.3gp` | 226190 | 624 |

  The theme decodes into 6001 * 160 * 2 = 1920320 PCM bytes; in a headless run
  the port's `pcm_write` counter ends at **960160 frames**, exactly the theme's
  6001 * 160, i.e. the soundtrack really is played, not merely parsed.
* `tests/test_amr_mp4.c` (106 checks): synthetic containers only - constant and
  table stsz, `stco`/`co64`, damr framesPerSample 2, the real file's exact
  17-byte damr and 53-byte samr entry; refusals for truncation at every level,
  two samr tracks, missing damr, fps 0, spc 0, first_chunk != 1, stsz/stsc
  count disagreement, no mdat, chunk offset outside mdat, sample past mdat
  (mutation-verified), non-AMR entry.  Decoded PCM is byte-identical to
  `nj_amr_decode()` over the same frames prefixed with `#!AMR\n`.
* `86/86 ctest` (was 85; `test_amr_mp4` wired in the existing AMR block).
* ASan+UBSan: the 106-check test is clean; a sweep over the real file (4000
  random truncations + 4000 random 16-byte corruptions, whole-file decode once)
  reports no out-of-bounds access and no decode/count mismatch.
* Trim build `-DNJ_ENABLE_AMR=0`: `nj_amr_mp4.c` compiles to its documented
  empty translation unit and the media branch is out; build clean.
* Doom headless: the four startup `MediaException`s are gone, replaced by the
  caught `NullPointerException` from the unsupported VideoControl; no uncaught
  exception, exit 0.  Startup now costs ~2 MB of Java heap for the theme's PCM
  (12023312/12023312 bytes in a `--heap 16` run) and runs at 29.1 fps/400
  frames.

## Still open in Doom

The game's menu hitboxes are key-poll driven (`getKeyStates()` polled from
`k()`), and the diagnostic bridge's sustained presses have not yet put the
cursor inside the New Game rect (219 < dirM < 236) before FIRE.  Doom runs its
entire main loop inside `Doom.<init>` (startApp is empty), so the run's frames
are spent during construction; the bridge's `quit` then unwinds the constructor
with `InternalError`, which the runner reports as "cannot instantiate
Doom.Doom".  That is a harness/navigation matter, not the audio path: gameplay
entry is still unproven and this note does not claim it.
