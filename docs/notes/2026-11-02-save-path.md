# Save-path benchmark and round-5 fusion experiment (negative result)

Status: **not merged**. This note documents how the Android 22 MB full-save path
was benchmarked, what the save bytecode profile looks like, and why the six
candidate superinstruction families were not committed: they win on desktop
`gcc -O3` but do not reach the 5% bar on the target APK codegen (`clang -Os`),
which is the same transfer-rate lesson as the round-4 load-path work.

## Deterministic full-save benchmark

`Storage.saveChunks0()` takes the fast in-place path only when
`Level.chunksInPlace` is set and `chunks.dat` is exactly 22,024,192 bytes
(256 chunks x 21 sectors x 4096). `Storage.saveChunksInPlace()` throws
`IOException("chunks.dat size")` for any other size; `saveChunks0()` catches
that, logs "chunks in place" and falls back to the full save (`chunks.tmp`,
header + per-chunk copy/`Pal.exportChunk`, then rename). That fallback is the
slow path we want to measure.

Benchmark recipe (emulator-5570, AVD NJ_API21 x86_64, `x86_64` -Os APKs):

1. Install the APK with `adb install -r` (keeps app data) and restore the same
   pristine 22 MB world under
   `/data/data/com.lucinhu.nj2me/files/fs/games/com.mojang/minecraftWorlds/Unnamed world/`
   (`chown 10061`, `restorecon`, mode 600).
2. Append two bytes: `adb shell "echo x >> '<chunks.dat path>'"`.
   The API21 toolbox has no `truncate`/`printf`, and `dd seek=` does not extend
   the file, so the append is the reliable way to change the size to
   22,024,194 -> the in-place path throws -> `saveChunks0()` runs the full save.
3. Launch `com.lucinhu.nj2me/.GameActivity` with the usual jar/jarpath/title
   extras, tap Start Game (160,160), tap the world card (160,190), wait for the
   app's `MCJ: HUD3D` log line.
4. Tap the in-game pause icon (268,40), then "Quit to title" (160,154).
   `MC.class.quitToTitle()` calls `saveNow()`, which times `saveWorld()` and
   logs `MCJ: SAVE <n> ms`; that logged number is the metric.
5. Interleave baseline/candidate runs (one warm-up discarded; the first run
   after idle is measurably faster on this host).

Harness: `/home/lucinhu/workspace/wt/evidence-r5-save/android-save-bench.sh`.

## Save-window profile

Instrumented desktop build (`NJ_PROF_INSTR` NJPP pair/triple histogram, frame
windows `NJPP_W0=560:620` to cover only the quit-triggered save;
`NJPP_W1=621:622`): the save window is ~444.5 M dispatches for a 2359 ms
instrumented save. Fetch-time pairs are syntactic, so already-fused families
(e.g. `sipush+if_icmplt`, `iinc+iload`, `iload+iaload`) still appear as pairs
and are not counted as uncovered.

Top save-window ops: `iload` 25.4%, `ior` 8.0%, `sipush` 7.5%, `aload_2` 7.4%,
`iinc` 5.5%, `iload_1` 5.4%, `istore` 4.4%, `baload` 3.1%, `iastore` 2.7%,
`aload` 2.7%, `invokestatic` 2.7%, `i2b` 2.7%, `bastore` 2.7%.

Top triples: `iinc iload sipush` 21.7 M; `aload_2 iload iconst_1` 18.0 M;
`iload iconst_1 ishr` 18.0 M; `iastore iinc iload` 12.2 M;
`sipush if_icmplt return` 12.1 M; `iload iload invokestatic` 12.0 M;
`ior i2b bastore` 9.0 M; `i2b bastore goto` 7.5 M; `baload sipush iand` 7.0 M.

Uncovered family sites: `iinc+iload+const` 21.7 M, `aload+iload+arrayload`
14.5 M, `store+iload` (any slot) 14.6 M, `baload+const+iarith` 13.9 M,
`iastore+iinc` 12.2 M, `i2b+bastore` 12.0 M -- ~89 M, i.e. ~20% of the save
window's dispatches.

The save is game Java, not native I/O: the bytecode delta between a save run
and a no-save run is ~354 M at ~264 M/s, which matches the measured desktop
`MCJ: SAVE` (~1266 ms); the `write()` natives are a handful per 32 KB buffer.

## Candidate fusions (experiment only, not merged)

Six families were implemented in `src/core/nj_interp.c` behind the existing
`#if NJ_ENABLE_SUPERINSTR` + `if (NJ_FUSION_ALLOWED)` gate, shared by the
switch and replicated interpreter bodies:

1. `NJ_BALOAD_CONST_ARITH_FUSE` -- `baload` + const + int-arith.
2. `NJ_ALOAD_ILOAD_ARRAY_FUSE` -- `aload` + `iload` + array load, reusing
   `NJ_ARRAY_LOAD_BODY` so NPE/AIOOBE behaviour is identical.
3. `NJ_IINC_LOAD_BODY` extended with const+`if_icmp` branch.
4. `NJ_STORE_LOAD_FUSE` extended to any-slot `iload`; generic `istore` too.
5. `i2b` + `bastore` inline (identical checks, `THROW` pc = bastore's).
6. `iastore` + `iinc` inline.

`tools/check_superinstr_digest.sh build/nj2me` -> `PASS: 27 digest values
identical to the desktop JVM`. The candidate diff is archived at
`/home/lucinhu/workspace/wt/evidence-r5-save/candidate.diff` (255 lines) and the
generator script at `.../patch_fusions.py`.

## A/B results (`MCJ: SAVE` ms, same restored 22 MB world)

Android x86_64 -Os APK on emulator-5570, order b1,c1,c2,b2,b3,c3 (warm-up
discarded): base 2500, 2570, 2754 (mean 2608); candidate 2517, 2632, 2599
(mean 2583) -> **-1.0%**, inside the measured +/-3% host drift (the late b3 run
shows the drift). No 5% win.

Desktop, 5 alternating pairs, pinned CPU:

| binary | base runs | base mean | cand runs | cand mean | delta |
|---|---|---|---|---|---|
| gcc -O3 | 1277,1283,1291,1311,1310 | 1294.4 | 1138,1134,1192,1109,1166 | 1147.8 | **-11.3%** |
| clang -Os | 1462,1431,1428,1493,1445 | 1451.8 | 1390,1415,1412,1358,1462 | 1407.4 | **-3.1%** |

Counted bytecodes on the gcc runs drop 4.78-4.81 G -> 4.59-4.62 G (~-3.9%):
the dispatch win is real but does not transfer proportionally to `clang -Os`,
and on the Android x86_64 APK it is lost in emulator/host noise. This matches
the round-4 load-path result and the build-flag study: dispatch-count wins on
`gcc -O3` are not a reliable proxy for the target `clang -Os` build.

## Conclusion

Target-codegen win was -1.0% (noise), below the 5% bar, so nothing is merged:
the save-path speedup needs a different lever (e.g. a native fast path for the
byte-packing/stream loops, or reducing the 22 MB full-save fallback on the game
side), and would need a target benchmark able to resolve <3%.

Evidence: `/home/lucinhu/workspace/wt/evidence-r5-save/` (`android/`,
`desk-ab-gcc/`, `desk-ab-clang/`, `desk/` fixture, `pristine-fs/`, profile and
harness scripts).
