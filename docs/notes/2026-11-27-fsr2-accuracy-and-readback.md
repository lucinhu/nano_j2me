# FSR2 时域重建的画质对照与回读耗时

高清 M3G 有两条放大路径：空间重建（立方核 + RCAS）和时域重建（AMD FSR2 2.2.1）。
空间路径已在[缩放矩阵](2026-11-27-fsr-scale-matrix.md)里逐档量化，时域路径一直只有
"能跑、时域历史稳定"的定性结论。这一轮补齐时域路径的两件事：它离同帧原生高分有多远，
以及它在桌面 Vulkan 上每个派发究竟花在哪里。

## 装置与对照真值

沿用第三轮的确定性 Doom3 装置（`.local-tools/debug-runs/fsr-quality-round3-3d/`）：
同一串按键、同一帧号，分别以 1×、4×、8× 内部渲染跑 240 帧，三次的 `--stats` 完全一致
（`frames=240 paints=3 gfx=749 tris=86784 m3g=8910 bytecodes=48017`），最后一帧已经是
第一人称游戏画面而不是标题页。

- 8× 渲染是 1920×2560，作为唯一真值；4× 渲染是 960×1280。
- 2×、3× 真值用 8× 图做精确面积缩小（积分图加权，`area_int`），不经过任何插值核对。
- 待测输出由 `.local-tools/debug-runs/fsr-quality-temporal/build/nj2me` 产生：
  `--render-scale 2 --graphics vulkan --fsr2`，同一帧 `00240.ppm`。
- 参考组：同参数的 `--render-scale 2` 原生软件渲染、原生 GPU 面片渲染，以及只从 1× 图
  做立方核放大得到的 2×（就是 FSR1 默认路径的画质上界）。

## 画质：FSR2 接近同帧原生渲染

| 倍率 | 对照 | MAE | 最大误差 |
| --- | --- | --- | --- |
| 2× | FSR2 对 2× 真值 | **0.7316** | 75 |
| 2× | 软件原生渲染对 2× 真值 | 0.4812 | 75 |
| 2× | GPU 原生面片渲染对 2× 真值 | 0.8147 | — |
| 2× | FSR2 对软件原生渲染 | 0.3607 | 26 |
| 2× | 立方核从 1× 放大对 2× 真值 | 3.249 | — |
| 3× | FSR2 对 3× 真值 | **0.5598** | 72 |
| 3× | 软件原生渲染对 3× 真值 | 0.6536 | — |
| 3× | FSR2 对软件原生渲染 | 0.1328 | 12 |

2× 时 FSR2 的误差只比同帧原生软件渲染高 52%（0.73 对 0.48），却比从 1× 图做空间放大
好 4.4 倍；3× 时它甚至比同帧原生软件渲染更接近真值（0.56 对 0.65），与原生渲染的
互相差异只有 0.13。这个结果解释了为什么时域路径值得保留，也说明"从 1× 直接空间放大"
和"同帧多采样再缩小"之间不是靠锐化参数能弥合的差距。

## 时域稳定性

取第 200–239 帧，用原生 2× 连续帧差小于 1.5/255 的像素作为静止掩码（占 83.9%），
统计掩码内连续帧差的平均值（闪变量）：

| 输出 | 闪变量 | 说明 |
| --- | --- | --- |
| 原生 2× 渲染 | 0.1132 | 参考下限 |
| FSR2 2× | **0.1482** | 引进了 31% 的额外闪变，远低于空间放大 |
| 立方核 1×→2× | 0.2904 | 空间放大的代表值 |

FSR2 的时域反馈确实在工作：抖动相位让每帧贡献不同样本，静态场景的闪变只有空间放大的一半。

## 桌面回读耗时：125 倍的取整问题

同一套输入在桌面 Vulkan 上，FSR2 代价一度大得不合常理（240 帧里 2× 多花 15.2 s）。
用 `.local-tools/debug-runs/fsr-quality-round4/bench_fsr2.c` 直接创建 FSR2 上下文、合成
颜色/深度/运动输入、跑 60 次派发，得到的中位/95 分位：

| 尺寸 | 修复前 | 修复后 | 倍数 |
| --- | --- | --- | --- |
| 120×160 → 240×320 | 17.554 ms | 0.143 ms | 123× |
| 240×320 → 480×640（2×） | 69.356 ms（p95 73.776） | **0.555 ms**（p95 0.823） | 125× |
| 240×320 → 720×960（3×） | 156.846 ms | **0.830 ms**（p95 1.081） | 189× |

`time` 显示 15.35 s 里 14.65 s 是用户态 CPU，`nvidia-smi` 期间 GPU 占用 0–2%——说明不是
GPU 算不动。把派发拆段计时（`.local-tools/debug-runs/fsr-quality-round4/nj_fsr2_vk_prof.cpp`）
后，480×640 一次 69.7 ms 里 69.1 ms 落在派发之后的回读循环，其余各段合计不超过 0.8 ms。

根因在 `src/port/fsr2/nj_fsr2_vk.cpp` 的 `create_cpu_io`：共享主机缓冲只申请了
`VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT`。桌面 NVIDIA 对只有 HOST_VISIBLE 的堆给出写合并
（write-combined）内存，逐字节读取时每次访问都要等总线，摊到输出像素上约 226 ns/像素。
修复两处：

1. 新增 `allocate_flags()` 后包一层 `allocate()`：主机可见的申请先叠加
   `VK_MEMORY_PROPERTY_HOST_CACHED_BIT`，设备没有缓存型堆时再退回原请求。
2. 回读从"每像素四次字节访问"改成"每像素一次 32 位读 + R/B 交换"
   （R8G8B8A8 小端字是 `0xAABBGGRR`）。

修复后同一 2× 游戏窗口从 28.599 s / 8.4 fps 变成 14.512 s / 16.5 fps，输出帧与修复前
逐位相同（`00240.ppm` sha256 `58ba2e676b0b3a26b7e97bcffc3272006c89e631a5a41d994970e943c0595720`），
所以是纯耗时修复，没有画质变化。

## Android 实测：同一修复在模拟器上没有差别

同一 APK 修复前后在 API 36 模拟器（gfxstream Vulkan 直通宿主机 NVIDIA）上跑
JBenchmark3D，用 `debug.nj2me.fsr2_trace=1` 统计派发节奏：

| 构建 | 12 s 内派发 | 绑定时距中位 | reset=1 | 错误 |
| --- | --- | --- | --- | --- |
| 修复前 `d2828124…` | 1600 | 8.00 ms | 0 | 无 |
| 修复后 `502ec4be…` | 1600 | 8.00 ms | 0 | 无 |

也就是说 gfxstream 给的主机内存本来就可缓存，写合并惩罚只在桌面驱动上出现；这次修复对
Android 没有回归。Android 的流畅度另有旁证：同一构建跑农场，`present stats` 每 2.00 s
报一次 `frames=120`（锁 60 fps），`draw` 中位 0.46–0.56 ms，`swap` 中位 15.5 ms（垂直同步）。

## 结论

- 时域路径的画质确实远高于空间路径：2× 时 MAE 0.73（空间 3.25），3× 时 0.56，
  闪变约为空间放大的一半。FSR2 与 2×/3× 高清倍率的配对限制（见
  [Android Vulkan 与 FSR2 路径验证](2026-11-27-android-vulkan-fsr2.md)）是合理的默认。
- 4×–8× 仍不接时域路径：FSR2 只到 3×，再叠一层空间放大会引入第二次重采样（比 2× 原生
  多出来的误差还大），当前结论不变。
- 桌面 FSR2 的派发耗时从 69 ms 降到 0.56 ms 之后，`--fsr2` 在桌面回放（240 帧）里不再是
  瓶颈，后续可以用桌面装置做时域历史、抖动相位的快速实验，而不必每次都上模拟器。
- 构建：`build/android-vulkan-x86_64-official/nj2me.apk`；桌面基准与剖析程序留在
  `.local-tools/debug-runs/fsr-quality-round4/`，不进发布包。
