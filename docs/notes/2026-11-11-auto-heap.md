# 可选 Java 堆自动扩展与原游戏 P 行为

P 继续沿原有 raw-key 路径把 27 交给游戏。在原版 Minecraft 中，这会进入游戏自己的菜单或返回逻辑。此前消费 P 来避开菜单贴图加载的实验已经撤回；不修改游戏 JAR，也不替游戏改变菜单行为。

桌面设置的“自动扩展内存”默认关闭，保存到独立的 `heap_auto_grow` 配置项。开启后在下次游戏启动时生效。原有“Java 堆”的“自动”仍表示启动时使用运行时默认大小，与这个新开关不同。

命令行可独立覆盖已保存的开关：

```sh
nj2me --heap 16 --heap-grow game.jar
nj2me --heap 16 --no-heap-grow game.jar
```

显式 on/off 的优先级高于配置文件，经过游戏库连续启动游戏时也保留这个覆盖。默认启动堆为编译配置的 `NJ_MAX_HEAP`（本次桌面构建为 16 MiB），命令行帮助已与实际行为统一。开启自动扩展时上限为 128 MiB；若调用者显式选择更大的初始堆，不会把它缩小。

## 分配策略

新的 `nj_vm_create_with_heap_limit(port, initial_bytes, limit_bytes)` 保持已有对象的地址稳定。创建时通过宿主分配器预留完整上限，但只清零并开放初始的逻辑堆。一次分配在垃圾回收后仍不能满足时，才扩大可用范围，优先倍增或满足当前申请，且不超过上限。新开放的区域清零，并与已有尾部空闲块合并。原来的 `nj_vm_create` 保持固定堆语义。

这不是移动式回收，也不会重新启动游戏。预留通过原有 `port.alloc` / `malloc` 完成，因此宿主可能在启动时就实际分配上限；不能承诺每个平台都延后提交物理内存。宿主统计按完整预留记录，Java 的可用堆按当前开放大小计算。达到上限或宿主无法预留时仍可能内存不足；扩容也不保证消除所有碎片问题。

存档格式和内置 Java 成员布局不变。恢复时使用接收 VM 明确允许的上限，不能靠存档头越过该限制；加载后继续沿用接收 VM 的扩展策略。扩容前后对象地址保持不变，存档恢复原有的地址重定位流程另行执行。

## 验证

普通 Release 的 170 项测试全部通过；扩容、堆边界、存档、生命周期和 LCDUI 另外通过了 ASan、UBSan 与泄漏检查。扩容专项包含 69 项断言，包括 16→32 MiB 扩容后的存档恢复，以及接收上限不足时拒绝加载并保留原状态。

用同一个 Release 二进制、原版 Minecraft JAR、相同存档副本和 16 MiB 初始堆，各重放 90 帧。两组按 P 后都显示原游戏菜单。关闭扩容时复现 `Image.createImage(String)` 的 OOM，游戏提示视距减少一格；开启时记录到 16→32 MiB 扩容（上限 128 MiB），没有 OOM 或降视距提示。结论限于这次存档和操作，不是帧率或长期内存测试。
