# B2 prototype plan: resident 3D scene + opaque 2D deferral

Decision (user, 2026-11-24): continue the GLES2 structural rework as a B2
prototype (persistent frame FBO + depth texture + 2D overlay composite), even
though the measured upper bound (docs/notes/2026-11-24-gles2-frame-resident-2d-layer.md,
Round 10) says the realistic outcome is parity, not the original <3.5 s target.

## Insight from the round-10 analysis

The 2,956 Galaxy flushes are all *observer-driven*: each is followed by a CPU
2D operation (99.7% opaque image blits, no text) or by `present`. A per-flush
colour readback (`read_c` 1,283.6 ms of 3,663.8 ms) is therefore the single
biggest cost. It only exists because the software 2D pass needs the current
3D pixels as its background.

The 2D study showed the common case is **opaque overwrite** (blit/fill of an
image or solid rect over the 3D scene). For an opaque op the result does not
depend on the destination pixels, so the op can be executed *before* the 3D
scene is read back, as long as the final composition keeps the op on top:
3D scene (GL) under the CPU overlay. Only non-opaque ops (alpha blits,
transparent fills, text with a background read, xor/mask) and any 3D
transaction that arrives *after* a 2D op force an ordered commit.

## Architecture

1. Backend keeps one screen-sized colour texture + depth texture (GL FBO) per
   GPU session, initialised once per frame from the CPU canvas depth keys (the
   only CPU depth that matters for ordering inside the frame).
2. `triangles_run` renders into the resident FBO. No colour readback at
   observer flushes — it only marks "scene pending".
3. The runtime classifies each 2D primitive as `opaque-safe` or `needs-background`.
   * opaque-safe: draw into a CPU **overlay** surface (transparent except
     written pixels) and record the damage rect; no commit.
   * needs-background / any later 3D transaction: commit the resident scene
     (one colour readback of the damage union), composite the overlay, then
     execute the op normally on the CPU canvas.
4. At `present`: commit the resident scene once (damage union), composite the
   overlay, then hand the canvas to the port (SDL texture / EGL present).
   A future EGL path can skip the readback entirely.

## Milestones

* M1: runtime primitive classification + overlay surface + damage tracking
  (new fields in `nj_vm`/port; no GL changes yet; gated by an opt-in env).
* M2: backend resident scene FBO + depth texture; `triangles_end` defers
  commit; commit-on-demand entry point used by M1.
* M3: parity harness: three-frame PPM comparison for LoopDemo, Galaxy on Fire
  2, Doom3 against software; whole-corpus visual probe stays at the documented
  failure set.
* M4: measure CPU; if GL is not below software, keep software default and
  record the outcome; if parity is close, add SDL EGL presentation.

## Risks / honest expectations

* The software 2D pass still runs for every op; the only removed cost is the
  per-observer readback (~35% of the transaction budget) plus depth readback /
  depth-key upload / seed (another ~20%). Best case GL-3D+software-2D falls
  from ~6.0 s to ~4.4-4.8 s user on Galaxy, i.e. parity with software (5.0 s),
  not a win.
* Alpha/text-heavy frames regress unless classification is conservative
  (fallback flush is always correct, just slower).
* Android ES2 depth-texture support (OES_depth_texture) must be checked before
  shipping; prototype is desktop-SDL only for now.
