# 3D fidelity sweep: what the M3G corpus actually draws

2026-11-03

Round-6 profiling (docs/notes/2026-11-02-heavy-scene-os.md) used Minecraft
PE's in-world view as the reference workload, because that is the only title
in `tests/games` that keeps a heavy M3G scene running frame after frame.
Fidelity work needs the opposite: many different titles, each exercising a
different corner of JSR-184.  This note is the sweep of every M3G-carrying
title in the corpus, with the FreeJ2ME-Plus reference where a comparison
could be lined up.  The result is a negative one for a *renderer* bug: the
titles that reach 3D render plausibly, and the two visible anomalies traced
to game code or input mapping, not to `nj_lib_m3g.c`.  The classification
table and the two remaining candidates are the useful output.

## Method

1. Scan every JAR for `javax/microedition/m3g` class references
   (`unzip -l`/class-name scan).  27 titles carry M3G; one further title
   (`鲁宾逊漂流记汉化BT版_4677.jar`) is not a zip file at all.  The full
   ref/class counts are in `evidence-r7-fidelity/m3g-jars-scan.txt`.
2. Sweep 1: every title for 240 frames at 30 fps with a generic key script
   (`20:fire 40:fire 60:soft1 80:fire 100:down 110:fire 140:fire 170:soft1
   200:fire 220:fire`), dumping a PPM every 60 frames and the `--stats`
   line.  Eight seconds is enough to classify the icon/logo screens.
3. Sweep 2: the 23 titles that had not drawn triangles in sweep 1, this time
   900 frames (30 s) with a longer script that presses through menus
   (`45:fire 120:fire 150:fire 240:soft1 270:fire 330:fire 390:down
   420:fire 480:fire 540:up 570:fire 630:fire 690:soft2 720:fire 780:soft1
   810:fire 870:fire`).  Same dump/stats handling.
4. For the scenes that rendered, screenshots were compared with
   FreeJ2ME-Plus (`local-tools/run-freej2me-headless.sh`, engine commit
   `baca76a4dda6f30abac67fb4a3db009eed05f91c`) run headless at the same
   240x320 size.  FreeJ2ME was confirmed to render the M3G path of this
   corpus (NFS The Run's new-game car, the ski-jump start gate), so a
   difference is meaningful only when both emulators are on the same screen;
   states were aligned by driving both with the same key sequence and
   comparing whole screens.

All runs exit 0; all original JAR hashes are recorded, unchanged, in
`evidence-r7-fidelity/jar-hashes.sha256`.

## What was checked for a renderer bug

- **Ski jump's black sky.**  On the Kuusamo "pojedyńcze zawody" screen the
  reference shows a light-blue sky where we show black (top 40 rows: ours
  2,740 pure-black pixels, reference 0).  The black follows the mountain
  silhouette, so it is the region above the landscape, not a strip artifact.
  This could be the title's M3G `Background` (image-filled) not being drawn
  over the whole viewport, or the camera being at a different point of the
  intro animation.  The two emulators were not on identical animation phases
  at the moments compared (the reference screen at the same wall time shows
  a nearer camera), so this is documented as a candidate, not a bug.
- **Runtime `Image2D` formats 96/97/98 as textures.**  `jr_setup()` only
  accepts `fmt == 99 || fmt == 100` for a texture; a title that builds an
  `Image2D` with ALPHA/LUMINANCE/LUMINANCE_ALPHA format and binds it would
  draw untextured.  No title in the corpus exercised that path (no visual
  evidence found), so it stays a code-level gap, not a fixed bug.
- **Doom 3 "NEW GAME" fire key.**  Fire moves the cursor but does not
  activate; this is our key mapping, not the renderer (the 3D background
  behind the menu renders).  Not a rendering bug.
- **Flat-shaded billiard balls** are consistent with an unlit/low-poly
  model; no reference frame at the same state to prove otherwise.
- **AlpineSki `ArithmeticException: / by zero` (1,998×)** is the game's own
  FPS calculation: `javap -c AlpineSki.e.d()V` shows the sequence
  `1000L; lload (now - g); ldiv; putstatic b:J`, so `d()` divides 1000 by
  an elapsed-millisecond delta that is zero when two calls land in the same
  millisecond.  The method catches the exception and keeps its previous
  value; on a real device the clock granularity hides it.  A game-code
  timing artifact, not our renderer (and not our clock: the same call at
  real speed would rarely see a zero delta).
- **"Rekord: 120 m" vs reference "Rekord: 120.0 m"** looked like a float
  formatting bug, but `nj_fmt_double()` prints `%g` and appends ".0" when
  there is no '.'/'e', so it prints `120.0`.  The two emulators were simply
  showing different game state (the game stores the record differently
  before/after a run).

## Two candidates for the next fidelity round

1. **Background-image coverage** (`m3g_background_image()`,
   `src/midp/nj_lib_m3g.c` ~4082): prove/disprove whether a World
   `Background` image smaller than the viewport leaves pixels untouched
   (and therefore black when the colour clear is disabled).  A synthetic
   fixture would settle it; the ski-jump screen is the corpus trigger to
   retest once states can be aligned exactly.
2. **Runtime Image2D format 96/97/98 textures**: implement LUMINANCE /
   LUMINANCE_ALPHA / ALPHA expansion to RGBA at texture-bind time (same
   place the paletted path expands), or document why the spec's
   "implementation chooses" wording allows dropping it.

## Conclusion

No provable rendering bug was found in the corpus this round, so no source
change is committed: the deliverable is the sweep table, the reference
harness, and the two candidates above.  The sweep is cheap to re-run
(`sweep.sh`, `sweep2.sh`) and is the right gate for future fidelity fixes:
a fix is only real when a title's screenshot moves toward the FreeJ2ME
frame at the same state.
