# JSR 75's phone book: present, and honestly empty

`javax.microedition.pim` did not exist at all.  That is a linkage error inside
a title's own feature code, not a missing API call it could catch:
3D孤胆枪手2010_4634 opens the phone book and walks it -

```java
PIM pim = PIM.getInstance();
ContactList list = (ContactList) pim.openPIMList(PIM.CONTACT_LIST, PIM.READ_ONLY);
if (list.isSupportedField(...)) { ... }
Enumeration e = list.items();
while (e.hasMoreElements()) { Contact c = (Contact) e.nextElement(); ... }
list.close();
```

- and with the classes absent the whole block died on `NoClassDefFoundError`
before any of its own error handling could run.

## What a device without a contact store can honestly answer

This runtime has no contact database, and it does not invent one: the store is a
port feature (a phone's contacts, a vCard file, a RecordStore) and nothing in
this project asks for one yet.  A fresh phone, however, does not answer "no such
class" - it has an **empty** contact list.  That is what is implemented:

| call | answer |
| --- | --- |
| `PIM.getInstance()` | a `PIM` object (stateless; a fresh instance is indistinguishable) |
| `openPIMList(CONTACT_LIST, READ_ONLY/WRITE_ONLY/READ_WRITE)` | a `ContactList` that is supported and empty |
| `ContactList.isSupportedField(f)` | `false` for every `f` (the store holds no fields) |
| `ContactList.items()` | a real `java.util.Enumeration` with no elements |
| `ContactList.getName()` | `"Contacts"`; `PIM.listPIMLists(CONTACT_LIST)` returns that one name |
| `ContactList.close()` | returns |
| `openPIMList(EVENT_LIST/TODO_LIST, ...)` | `PIMException` - the specification's answer for a list that is not found, and true here |
| `openPIMList(..., mode)` with a mode outside the three | `IllegalArgumentException` |

Contact values (`getString`, `addString`, ...), field labels and the
vCard/vCal serial formats are **not** implemented.  They are unreachable through
this store - `isSupportedField()` is false for everything, so a title that
browses an empty phone book never calls them - and they need the store that does
not exist.  `COMPATIBILITY.md` says so in the JSR 75 row rather than leaving the
gap to be discovered.

## Why the interfaces repeat their methods

A built-in class here has one super and no interface list (`implements_interface()`
in `nj_class.c`), and a call typed as an interface resolves in that interface's
OWN table.  So `ContactList` declares the union a caller uses through it
(`close`, `getName`, `items`, `isSupportedField`, `getFieldLabel`) instead of
relying on inheritance from `PIMList`, and `Contact` declares the two
`PIMItem` methods a caller reaches through it (`countValues`, `getString`).

## Verification

`tools/check_pim.sh` (ctest `check_pim`) builds `tests/pimdemo/PimDemo.java`
against the stub API and runs the exact sequence above through the interpreter,
asserting one line:

    PIM opened=true supported=false items=0 todo=PIMException mode=IAE names=1 closed=true

A/B, same fixture and command: the build before this change reports

    PIM ERROR java.lang.NoClassDefFoundError: javax/microedition/pim/PIM

No real-game A/B is claimed: 3D孤胆枪手's phone-book feature is not reached in a
600-frame headless run (identical `paints/gfx` counts before and after), so the
fixture is the evidence for the sequence the title performs.

Full ctest 129/129.

## Limits

There is no contact storage: reads see an empty list and writes have nothing to
write to.  A port that wants the store fills in the same seam
`RecordStore`/`FileConnection` already use (a host directory), but no such hook
exists yet and this note deliberately does not pretend otherwise.
