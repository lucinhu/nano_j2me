# 平台 POWER 键不再作为 Java Canvas 的 raw key 27 投递

平台键枚举中的 `NJ_KEY_POWER` 值为 27。此前它未命中 MIDP 按键映射，会落入 raw-key fallback，作为 27 发送给 `Canvas.keyPressed/keyReleased`，并可能改写 `getKeyChar()`。把 27 当作 Back 的游戏因此可能进入返回或暂停逻辑。

本次在 [LCDUI 输入边界](../../src/midp/nj_lib_lcdui.c) 加入两个前置 guard：按下/释放入口和 repeat 入口消费 canonical POWER，返回已处理。按下/释放 guard 位于当前 Displayable 查询、raw-key fallback、字符写入和 held/latch 更新之前；随 POWER 附带的非零字符也一并消费。此处不调用 MIDlet 生命周期或退出操作。

`key=NJ_KEY_NONE, ch=27` 仍是显式字符输入；普通数字、方向、游戏键、两种 soft-key 约定、raw `'x'` 与 typed `'p'` 保持原路径。平台枚举与字符输入由不同参数区分，canonical `key=27` 始终表示 POWER。

回归扩展了已有的 [LCDUI 测试](../../tests/test_lcdui.c)，没有新增 CTest 注册、runtime builtin 方法或字段。测试通过自己创建的 Canvas 与两种 GameCanvas（`suppressKeyEvents` 为 false/true）观察真实回调，并检查：

- POWER 按下、释放、repeat 不产生回调，不改写字符；附带字符 0、`'P'`、27 均覆盖。
- 持有 UP 时的 held 状态和未读取的 press latch 保持；POWER 释放不会清掉已有方向键。
- 当前 Displayable、VM running/state、callback nesting 保持；没有 current Displayable 时也消费 POWER。
- 普通映射、两种 soft-key 约定以及显式 `NONE/ch=27` 的回调/字符对照通过。

相同、预先冻结的测试源码分别链接保留的旧库和修复后的库，normal/strict 两个 profile 结果一致：

| 路径 | 旧库 | 修复后 |
| --- | --- | --- |
| LCDUI，含全部原断言及三次 create/run/destroy | 11202 通过，81 失败 | 11283 通过，0 失败 |
| Form overflow/wrap/chrome/pointer/Gauge | 本 checkpoint 未重复旧库 | 通过，三次 teardown 相同 |
| Game package | 本 checkpoint 未重复旧库 | 785 × 3 断言通过，三次 teardown 相同 |

旧库的 81 个失败均来自新增的 POWER 回调、字符保持及无 current 消费断言；其他断言通过。strict 使用全库 ASan、UBSan、float-cast-overflow、禁止 sanitizer recover、frame pointer、`-Werror` 与 LSAN，没有诊断错误。每个 profile 仅替换 LCDUI archive member；normal 其余 75 个、strict 其余 73 个成员的字节和顺序均核验不变。每个 profile 的三个新路径各运行一次，没有重复已通过的 native 测试。

首次 fixture 编译把 root-release helper 名写错，编译即停止，未产生有效 baseline；原源码和失败日志保留。改为实际 `nj_root_release` 后重新冻结，同一修正版用于所有有效 old/new 运行。

本 checkpoint 是输入边界修复及相关路径验证，没有全跑 169 个测试，也没有重新运行 Minecraft、旧 benchmark 或存档恢复。既有 CLI/正式分数仍属于各自冻结版本。此结果不证明 Minecraft Image OOM 的原因或修复；堆容量、碎片和资源解码不在本次改动范围。
