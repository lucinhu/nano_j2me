# 4×–8× 时域放大链的取舍：实测后不实现

日期：2026-11-27。目标：回答上一轮遗留的最后一个结构性问题——高清倍率 4×–8×
目前只能纯空间放大（FSR2 每个轴最多重建 3×），值不值得加一条"FSR2 重建到 3×、
再交给 FSR1 立方核放大进 4×–8× 高清镜像"的时域链。

## 结论

不实现。链的 3D 像素最终与"直接在 3× 高清倍率上开 FSR2"完全一致，而后者已经比
原生 3× 渲染好 0–21%，却仍明显不如原生 8× 渲染；链的唯一收益是 2D/HUD 拿到 8×
的高清镜像，代价是多一次空间放大、多一个 8× 镜像的呈现上传（桌面实测 +2 ms/帧，
Android 8× 已从 60 fps 掉到约 52 fps）。收益不抵成本。

顺带确定了 FSR2 配对档位：**打开 FSR2 时把高清倍率自动配对到 3×，而不是原来的
2×**。在"理想 8× 画面"这一统一真值下，3× 时域比 2× 时域近 4–21%，代价约 +0.3 ms。

## 装置与方法

- 素材：确定性 Doom3 软件回放第 240 帧（游戏内第一人称 3D，键序
  `200:down:down,205:down:up,215:fire:down,216:fire:up`），原生 8× 渲染
  `fsr-quality-round3-3d/doom-8x/dump-frames/00240.ppm`（1920×2560）作真值来源。
- 候选（都是当轮真实产物，不是模拟）：
  - `n8`：原生 8× 渲染（当前 HD 8×，无时域）；
  - `n3`：原生 3× 渲染（HD 3×，无时域）；
  - `f3`：FSR2 3× 输出（HD 3× + 时域，Vulkan 后端）；
  - `f2`：FSR2 2× 输出（HD 2× + 时域）；
  - `n1`：原生 1× 渲染（HD 关闭，走 FSR1 空间放大）。
- 每个候选都经过生产呈现路径（`nj_gles2_present`，模式 5：立方核 + RCAS，锐度取
  默认 `0.87055056`）缩放到窗口；窗口取 960×1280、551×751、1080×1440。
- 真值 = 原生 8× 渲染做精确分数面积缩放到同一窗口（积分权重，不是最近邻/双线性
  近似），指标为 RGB MAE 与 8×8 亮度 SSIM。
- 复现：`.local-tools/debug-runs/fsr-round7/chain-matrix.py`（内部调用
  `.local-tools/debug-runs/fsr-round5/probe5` 与带 `NJ_PRESENT_STATS` 的回放装置）。

## 画质：与理想 8× 画面的距离（MAE / SSIM）

| 候选（渲染 → 窗口） | 960×1280 | 551×751 | 1080×1440 |
| --- | --- | --- | --- |
| 原生 8×（HD 8×，无时域） | **1.719 / 0.9992** | **1.734 / 0.9991** | **1.721 / 0.9993** |
| 原生 3×（HD 3×，无时域） | 2.280 / 0.9784 | 2.018 / 0.9921 | 2.261 / 0.9799 |
| FSR2 3×（HD 3× + 时域） | 2.257 / 0.9790 | 1.990 / 0.9925 | 2.240 / 0.9804 |
| FSR2 2×（HD 2× + 时域） | 2.362 / 0.9698 | 2.512 / 0.9678 | 2.331 / 0.9745 |
| 原生 1× + FSR1（HD 关闭） | 4.067 / 0.9412 | 4.081 / 0.9496 | 4.011 / 0.9528 |

读法：

- 原生 8× 缩到窗口几乎无损（SSIM ≥ 0.999），这是"理想画面"，也解释了为什么 8×
  在画质上无可替代。
- FSR2 3× 相对原生 3× 只好了 1%（2.257 对 2.280、1.990 对 2.018、2.240 对 2.261）：
  时域重建的价值不在"比同倍率原生更清晰"，而在用 1× 的渲染成本拿到 2×–3× 的画面。
- FSR2 2× 比 FSR2 3× 差 4–21%（551×751 窗口差得最多：2.512 对 1.990），因为 480×640
  镜像对 551×751 窗口几乎没有重采样余量。
- 时域链（`f3` 后再放大进 8× 镜像）的 3D 像素就是 `f3` 这一行，因此**永远不可能
  优于原生 8×**，也不可能优于直接选 3× + FSR2；它只多出一次放大和一次 8× 上传。

## 呈现耗时（桌面，`NJ_PRESENT_STATS`，380 帧中位绘制耗时）

| 源 | 960×1280 | 551×751 | 1080×1440 |
| --- | --- | --- | --- |
| 原生 8×（1920×2560，19.6 MB） | 4.23 ms | 3.43 ms | 4.33 ms |
| 原生 3×（720×960，2.8 MB） | 2.14 ms | 1.03 ms | 2.05 ms |
| FSR2 3×（720×960） | 2.17 ms | 1.03 ms | 2.04 ms |
| FSR2 2×（480×640） | 1.85 ms | 0.42 ms | 1.94 ms |
| 原生 1×（240×320） | 1.74 ms | 0.77 ms | 1.76 ms |

8× 镜像比 3× 镜像每帧多约 2 ms，全部来自 19.6 MB 的整帧上传（呈现路径是上传带宽
瓶颈，GPU 滤波只占 0.2–0.4 ms，见
[桌面呈现耗时](2026-11-27-desktop-present-stats.md)）。Android 侧的对应数字是 8×
绘制 3.09–3.36 ms、3× 0.66–0.85 ms，8× 还额外把帧率从 60 fps 拉到约 52 fps。

## 对配对默认值的修正

原实现（第 3 轮）在"打开 FSR2 时把非 2×/3× 的高清倍率改成 2×"，当时只是为了满足
FSR2 的 3× 上限，没有画质依据。本轮在同一真值下比较：

- 960×1280 窗口：3× 时域 MAE 2.257，2× 时域 2.362（好 4.4%）；
- 551×751 窗口：1.990 对 2.512（好 21%）；
- 1080×1440 窗口：2.240 对 2.331（好 4.0%）；
- 代价：dispatch 0.555→0.830 ms（桌面），呈现上传 +0.03 ms（960×1280）、
  +0.11 ms（1080×1440），Android 绘制 0.39→0.66–0.85 ms。仍在 60 fps 预算内。

因此把自动配对改成 3×：`GameActivity.addHdChoice` 与 `surfaceCreated` 的
启动修复都改为写入 `hd_scale = 3`（面板行同步选到 3×）。把倍率选成 1× 或 4×–8× 时
仍然自动关闭 FSR2 并提示，避免"已请求启用但没有时域"的不一致状态。
