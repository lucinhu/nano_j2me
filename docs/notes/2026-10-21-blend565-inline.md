# Inline the ARGB8888 -> RGB565 blend of a full-screen blit

Status (2026-10-21): shipped.  `nj_region_draw()` has a per-pixel shortcut for
the most common 2D compose on the desktop ports, and the pixels are unchanged.

## What the profile said

`gprof` on a Release `-pg` build running Doom 3 for 900 frames (240x320, 16 MiB
heap, uncapped) put 44 % of self time in `jr_triangle_v()` and 9.5 % in
`nj_region_draw()`, with 14.9 M calls to `nj_gfx_blend_pixel()` behind it.

The title paints a whole 240x320 ARGB8888 surface onto the RGB565 screen once
per frame - 236 blits in 240 frames, about 63,000 translucent pixels each.  The
per-pixel path did three nested calls per pixel (`nj_src_pixel()`,
`nj_gfx_blend_pixel()` -> `nj_surface_get()` / `nj_surface_format_color()`) to
rediscover a format that cannot change inside the blit.

## Change

`src/gfx/nj_gfx.c`:

* the ARGB8888-source branch of `nj_region_draw()` keeps its opaque packed write
  and gains `nj_blend565()`, which does the same arithmetic as
  `nj_gfx_blend_pixel()` at full source weight - expand the five/six/five
  destination bits, interpolate, pack again - directly on the destination row
  pointer, with no surface handle and no format switch;
* nothing else changes: other source/destination format pairs, ROP `SET`, masks,
  transforms and the caller-supplied alpha still take the old paths.

No allocation and no per-draw setup were added, so the trim builds and `size`
are unaffected beyond the text of the function.

## Verification

Same-source A/B, one binary built from the pre-change tree (`/tmp/nj-b2base`)
and one from the change (`/tmp/nj-blendonly`), both Release, both running the
same Doom 3 command (`--port headless --size 240x320 --heap 16 --fps 30
--run-frames 900`, isolated RMS).  CPU from `bash`'s `time` builtin, three runs
each, interleaved:

| run | before (`user` s) | after (`user` s) | pair |
| --- | --- | --- | --- |
| 1 | 2.810 | 2.730 | -0.08 |
| 2 | 2.849 | 2.561 | -0.29 |
| 3 | 2.911 | 2.624 | -0.29 |
| 4 | 2.924 | 3.089 | +0.17 |
| 5 | 3.360 | 3.350 | -0.01 |
| median of runs | 2.911 | 2.624 | |

The paired differences average -0.10 s (-3.4 %); the median of runs is -9.9 %.
Both figures are noisy: this host's CPU time for the same work moved by 20 %
across runs (see pair 5, which ran while another job shared the machine), so
read the change as "a few percent", not as the median.  The work itself is
constant: the 900-frame runs draw `tris=289235` on both sides and the dumped
frames (`--dump-frames --dump-every 150`, frames 150, 300, 450, 600, 750, 900)
are byte-identical before and after (`cmp`).  The change removes two nested
calls and a surface-format lookup per blended pixel, which is why it is kept;
the light-table change earlier the same day was the large measured one.

An equivalence test was added to `tests/test_gfx.c`: an 8-colour ARGB8888 image
with alphas 0, 1, 64, 127, 128, 200, 254, 255 is blitted with `NJ_ROP_PAINT`
onto two RGB565 backgrounds, and every result pixel is compared with the same
pixel blended by `nj_gfx_blend_pixel()` - the general path it replaced.  A
mutation that biases the formula (`(sr*a + dr*(255-a)) >> 8`) makes the test
fail; a rounding-only mutation does not, because the two formulations differ by
at most one 8-bit step and RGB565 quantisation hides it.

`ctest -j4` in the clean build: 87/87.

## Evidence

`.local-tools/debug-runs/blend565-r12/` keeps both A/B logs, the interleaved
`time` output, and the frame dumps for the identity check.  The `-pg` profile
itself was a throwaway `/tmp` build; its numbers are quoted above.
