# JSR 184 API gap audit and saved-state ABI impact inventory

Date: 2026-11-02
Author: bug-hunter (task-22)
Base: main `e95b613` (round-6 M3G fuzz fixes included), branch `r6-api`
Scope: docs only. No `src/` change in this task.

This note inventories every difference between the runtime's
`javax.microedition.m3g` surface and the JSR 184 1.1 specification, states which
of the differences actually matter for the title corpus, and classifies each
possible fix by its effect on saved-state compatibility, so the next round can
pick work with the cost known up front.

Ground truth for the specification: the JSR 184 1.1 javadoc (2005-06-22) at
`https://nikita36078.github.io/J2ME_Docs/docs/jsr184/`. All 30 class pages and
the constant-values page were downloaded locally for the audit (paths in the
evidence section). Corpus evidence comes from the 400 JARs in `tests/games`.

## 1. Summary

* **Methods and classes: the runtime has no missing spec member.** All 30 spec
  classes are present with all constructors and methods (checked
  inheritance-aware against every class page). There are 18 runtime-only
  extension members, none of which a corpus title uses; one spec-external class
  alias (`Sprite`), and one hierarchy deviation (`RayIntersection` extends
  `Object3D` instead of `java.lang.Object`).
* **Static constants are the largest real surface gap.** The spec declares 79
  `public static final int` constants across 13 classes. The runtime declares
  only 38 of them, and only Light's 4 are seeded with the correct value - 22 of
  the 26 values that `nj_m3g_late_init()` tries to store are dropped because the
  target classes never declare the fields, and 34 declared constants are never
  seeded. Nevertheless: no corpus title reads any M3G constant through
  `getstatic` (javac inlines static final ints), so the user-visible impact on
  the current corpus is zero; the gap matters for reflection/tools and for spec
  conformance.
* **Behavioural gaps: the Graphics3D lifecycle state machine is not enforced.**
  The runtime accepts double `bindTarget()`, null/invalid targets, invalid
  hints, `render()`/`clear()` without a bound target, rendering a World without
  an active camera, and non-renderable `render(Node)` arguments where the spec
  mandates `NullPointerException` / `IllegalArgumentException` /
  `IllegalStateException`. It quietly does nothing instead. This is
  behaviour-only and does not affect the serialized class shape.
* **Saved-state ABI:** the snapshot format stores per-class
  `field_count`/`method_count`/`is_array` and an ABI hash, and the loader
  currently requires the counts to match exactly. Adding the 41 missing
  constants (static fields) changes `field_count` on 8 classes and therefore
  invalidates every existing snapshot - exactly the round-2/round-5 problem.
  A generic **append-only growth migration** (prefix ABI hash + per-class static
  slot remap) can make such additions load old states; the design is in section
  6. Constants whose fields already exist (Material, Fog, KeyframeSequence,
  AnimationTrack - 34 values) can be seeded with no ABI change at all.
* **`Object3D.release()` / `release(target)` does not exist in JSR 184** and
  there is nothing to implement. The only release in the API is
  `Graphics3D.releaseTarget()`, which is implemented and spec-compliant
  (including "if no target is bound, silently ignored"). The design sketch in
  section 7 therefore documents why not to invent one, and what an
  ABI-compatible alternative would look like if deterministic release ever
  becomes a product requirement.
* **Recommended order:** (1) seed the already-declared 34 constants (zero ABI
  impact, small diff); (2) if spec conformance is a goal, add the 41 missing
  constants together with the append-only migration; (3) enforce the
  Graphics3D lifecycle exceptions behind title-corpus regression checks; (4) do
  not add `Object3D.release()`, do not remove the extension members or the
  `Sprite` alias, and leave `RayIntersection`'s superclass alone.

that reads the field objects, (b) any build that does not inline (some obfuscators
or hand-written class files), and (c) spec conformance claims.

## 4. Behavioural gaps: Graphics3D lifecycle

Source: `NJFN(m3g_bindTarget)` at `src/midp/nj_lib_m3g.c:4007` stores whatever it
is given (target ref + Graphics clip fields) with no validation;
`NJFN(m3g_releaseTarget)` at `:4039` only clears `_nj_target`;
`NJFN(m3g_clear)` at `:4154` returns `NJ_OK` when either the background is null
or no surface is bound. The render paths likewise render nothing instead of
raising the spec-mandated state exceptions.

Probe (compiled against the generated stubs, run headless under the round-6
worktree Release binary; full log in evidence, `probe/apiprobe.log`):

| Call | Spec requirement | Runtime behaviour |
|---|---|---|
| `bindTarget(null)` | NullPointerException | accepted (ok) |
| `bindTarget(new Object())` | IllegalArgumentException (not a mutable Image2D/Graphics) | accepted (ok) |
| `bindTarget(img, false, 0x1000)` | IllegalArgumentException (invalid hints) | accepted (ok) |
| `bindTarget(img)` twice | IllegalStateException (target already bound) | second bind replaces the target (ok) |
| `render(World)` without bound target | IllegalStateException | no-op (ok) |
| `clear(Background)` without bound target | IllegalStateException | no-op (ok) |
| immediate `render(...)` without target | IllegalStateException | no-op (ok) |
| `render(World)` with no active camera | IllegalStateException | no-op (ok) |
| `render(World)` whose camera is in another World | IllegalStateException | no-op (ok) |
| `render(Node)` with a Camera node | IllegalArgumentException | no-op (ok) |
| `render((Node)null, null)` | NullPointerException | no-op (ok) |
| `clear(null)` | clear with default settings (color = transparent black, depth = 1.0) | returns without clearing |
| `releaseTarget()` with no target bound | silently ignored (spec) | compliant |
| `releaseTarget()` twice | silently ignored (spec) | compliant |

Not observed: maximum-viewport-size enforcement on bind (spec requires rejecting
targets larger than `getProperties()` maximum). The runtime has no such limit
check at all.

Compatibility risk of fixing: a title that relies on the permissive behaviour
(e.g. calls `render` before `bindTarget`, or binds twice) would start receiving
exceptions. Corpus scan: 27 of 400 titles use M3G, all 27 call
`releaseTarget()` and `bindTarget()`, and the typical pattern is one bind per
frame followed by animate/render/release (the javadoc sample pattern). No title
was seen rendering without a preceding bind in the bytecode pattern we can
detect statically; a runtime corpus run is still the safer gate.

Saved-state impact: none. No class shape changes; only code paths throw.

## 5. Saved-state ABI inventory

### 5.1 What the snapshot stores

Blob layout (`src/core/nj_save.c:30-70`): 176-byte header; class table of
`nclasses` entries (`u16 name length + name, u16 instance_size, u16 field_count,
u16 method_count, u16 is_array, u16 state, u16 pad, u32 statics_base`); statics
array (`nstatics * 8` bytes); heap arena; interned strings; object table (per
live arena block: `u16 class index` + optional `u16 mirror class index`);
records; threads; CRC.

### 5.2 What the loader compares (`src/core/nj_save.c` ~1783-1832)

* `field_count`, `method_count`, `is_array` must match **exactly** for every
  saved class.
* `instance_size` may differ only if the runtime class grew; the delta is
  recorded in `legacy_grow[]` and the class's saved ABI hash is recomputed with
  the legacy offsets (`class_abi_hash_legacy()`, `src/core/nj_save.c:399`).
  A shrink fails.
* The per-class ABI hash covers: class name, `instance_size`, counts,
  `is_array`, and for every field `name`, `desc`, `(flags<<16)|offset`,
  `(ptype<<8)|width`; for every method `name`, `desc`,
  `(max_locals<<16)|max_stack`, `(arg_slots<<8)|ret_ptype`. **Member values,
  including static constant values, are not hashed**; static slots are stored
  verbatim in the blob.
* After the arena is read, every restored object's class index is checked; a
  class in `legacy_grow[]` with a non-zero delta may not have any live instance
  (`nj_vm_load: saved state holds an instance of ...` -> refuse), so old
  offsets are never dereferenced.
* `statics_base` per class is part of the class table; adding static fields to
  an early class shifts the base of every later class in class-table order.

## 6. Design sketch: append-only ABI growth migration

Goal: allowed future additions (constants first) keep all pre-existing saved
states loadable. Mechanism lives in `nj_vm_load()` next to the round-5
migration.

Preconditions this mechanism relies on (to be documented as rules for builtin
class edits):

1. New members are **appended at the end** of the class's field array and/or
   method array; existing members keep their order, names, descriptors, flags
   and offsets.
2. No member is removed, renamed or retyped. `is_array` never changes.
3. Static-only additions do not change `instance_size`. New instance fields, if
   ever added, are appended and increase `instance_size`; the zero-instance
   rule then applies.

Algorithm (per saved class):

1. If counts match exactly and (instance_size match or round-5 grow path),
   keep the current path: `class_abi_hash`.
2. Else, if `runtime_field_count >= saved_field_count`,
   `runtime_method_count >= saved_method_count`, `is_array` equal, and
   `runtime_instance_size >= saved_instance_size`:
   compute a **prefix hash** =
   `hash(name, saved_instance_size, saved_field_count, saved_method_count,
   is_array)` followed by the first `saved_field_count` fields (with
   `offset - grow` for non-static fields when `grow > 0`) and the first
   `saved_method_count` methods of the runtime class.
   Compare with the saved ABI hash. On a match mark the class
   `prefix_migrated` (and `legacy_grow` when the size grew).
3. Static remap: saved `statics_base[i]` values come from the saved class table.
   The old static count of class `i` is `saved_base[i+1] - saved_base[i]`
   (last class: `nstatics - saved_base[i]`). At load time allocate the current
   static slots per class; copy `old_count` saved values into the class's new
   base, in order, and leave newly appended slots zero (or let the normal
   initialisation fill them). If the class order changed, map by class name.
4. Arena objects: if `legacy_grow[i] > 0`, keep the existing zero-instance
   refusal. If `instance_size` is unchanged (constants-only case), old
   instances are valid and nothing changes.
5. Hash aggregation stays the same (FNV over class hashes), so an untouched
   class is still compared with the strict hash; every class is verified
   independently and any mismatch anywhere still fails the whole load.

Testing the mechanism before shipping a shape change:

* Golden-path: save a snapshot with the current binary at the pre-change ABI,
  then load it with the new binary; expect a `prefix-migrated` debug line per
  grown class and a successful resume.
* Negative: a snapshot built with a *different* member layout (reordered or
  removed) must still be refused (the prefix hash catches it).
* Value preservation: a snapshot that stores nontrivial static values (or the
  existing Minecraft state) must come back with all of them intact, which
  exercises the static remap; class-table order puts many classes after Camera
  and Background, so a base shift would corrupt them immediately.
* Zero-instance rule: a state that actually holds an instance of a class whose
  `instance_size` grew must be refused with the existing diagnostic.
* Round-trip: new binary saves and resumes its own state.

## 7. Design sketch: Object3D.release() / release(target)

The JSR 184 1.1 `Object3D` page lists exactly 12 methods: addAnimationTrack,
animate, duplicate, find, getAnimationTrack, getAnimationTrackCount,
getReferences, getUserID, getUserObject, removeAnimationTrack, setUserID,
setUserObject. There is **no** `release()` and no `release(target)` anywhere in
the API; the only "release" is `Graphics3D.releaseTarget()`, which we already
implement with the spec's semantics (flush + unbind; no target bound = silently
ignored, so double release is explicitly legal).

Object lifetimes in JSR 184 are managed by the Java GC; a title drops its
references and the objects go away. Given that:

* Adding `release()` to `Object3D` would be a non-spec extension. It changes
  `Object3D.method_count` (12 -> 13), i.e. it invalidates saved states unless it
  goes through the migration in section 6.
* It would also need semantics that the spec does not define: does it detach the
  node from its parent, clear animation tracks, free cached render data, make
  further calls throw? Any of these interacts with saved states that may contain
  the object (a released object that is then restored has to be either refused
  or resurrected).
* There are no external (GPU) resources to force-free: the renderer is software
  and all arrays are Java objects; the JSR-75/fuzz rounds found no renderer
  leak (LSan clean over repeated load/render/release churn).

Recommendation: **do not add it.** If deterministic memory release is ever
needed, prefer an internal, non-Java-visible cache-eviction pass (host side,
keyed by object identity, triggered on World replacement/GC) - it needs no
class-shape change and cannot break saved states.

If the Lead nevertheless wants an explicit release API for a specific game,
the only ABI-safe variant is: implement the append-only migration first, then
add `Object3D.release()` with idempotent semantics (nulls internal caches,
detaches from parent, keeps the Java object valid), and define that snapshots
containing a released object restore it as a plain un-released object. That
still needs product-level justification.

## 9. Compatibility and validation plan

* Unit checks in `tests/test_m3g.c`: after VM init, look up each spec constant
  field (e.g. `Camera.PERSPECTIVE`, `Image2D.RGBA`) and assert
  `nj_field_lookup(...) != NULL` and value equals the spec; these fail today
  for 41 fields and give the pre/post checks for item 2.
* Behaviour checks for item 3: a desktop test that calls the probe matrix above
  and expects the spec exceptions; plus a `tests/fuzzdemo` path that keeps
  calling these methods so the permissive/broken behaviour cannot regress.
* Migration checks for item 2: the section 6 test list - legacy snapshot at old
  ABI (saved by the pre-change binary) resumes with a `prefix-migrated` log,
  statics preserve values, positive/negative shapes, Minecraft saved-state
  resume, original `.local-tools/mc051/world.state` hash unchanged.
* Corpus gate: run the 27 M3G titles (or at least the playable subset) on the
  changed runtime and diff screenshots/behaviour against the current binary
  before shipping item 3.
