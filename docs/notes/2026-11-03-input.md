# Android soft-key and gamepad input

Date: 2026-11-03.  Device: emulator-5560 (AVD OpenHV_API26_googleapis, x86_64,
Android 8.1); APK built from this branch with `tools/build_android_apk.sh --abi
x86_64`; title `tests/games/MinecraftJ2ME_PE_0.6.1_V2.2.jar`, saved world
"Unnamed world".  Evidence: `.local-tools/debug-runs/r7-input/` (host paths in
`ctl.sh`); the APK used for the after-shots is `r7-input/apk/nj2me.apk`
(919,705 B, installed over the r5/r6 APK after copying the canonical
`build/android/debug.keystore` into the worktree).

## The two issues

### 1. BACK was played both ways on one press

A J2ME title reads the Android BACK key as its right soft key: `KEYCODE_BACK`
(4) maps to `NJ_KEY_SOFT_RIGHT` in `k_keymap`.  The port also used BACK as its
own panel handle.  `GameActivity.dispatchKeyEvent()` forwarded every non-volume
key to the game and, on BACK key-up, additionally called `onBackPressed()`
-> `showPanel()`.  One press therefore opened the game's own menu *and* the
port settings dialog on top of it.

Before (r6 APK, world loaded): `adb shell input keyevent 4` ->
`b1-back-before.png` shows the port panel; dismissing it at (245,585) reveals
`b2-back-before-underneath.png`, the game menu underneath.  Two actions, one
press.

Fix: BACK is decided on release.  A short press (less than 550 ms) is delivered
to the MIDlet as one complete soft-key press/release pair; a long press opens
the port panel and sends no key to the game; never both.  The 550 ms timer only
runs from ACTION_DOWN, so a normal tap never waits.

After: `input keyevent 4` -> `fix-back-short.png` (game menu, no panel), logcat
`back: down` then `back: short press -> MIDP soft-right`.  Long press needs a
real hold (`adb shell input keyevent --longpress 4` sends down+up immediately),
synthesised with `sendevent` on the qwerty device (KEY_BACK = 158):
`fix-back-long-panel.png` is the panel only, logcat
`23:07:41.415 back: down`, `23:07:41.965 back: long press -> port panel`,
`23:07:41.975 back: up after long press, panel only`.

`onBackPressed()` still opens the panel: it stays as the fallback for paths the
port does not consume itself (framework accessibility actions, OEM gesture
navigation).  Nothing about the panel's contents changed.

### 2. Gamepad buttons were dropped

`nj_port_android_push_key()` only knew `k_keymap` (phone keys); the gamepad
codes 96-110 fell off the end (`if (k == NJ_KEY_NONE) return;`).  A Bluetooth
pad could move nothing even though the desktop port has had controller support
since 2026-10-31.

Fix: a second table `k_gamepadmap` in `src/port/android/nj_port_android.c`,
consulted only when `k_keymap` misses.  It is deliberately not in `k_keymap`:
`nativeKeyTable()` feeds the on-screen pad editor (`KeyCatalog.java`), which
offers the keys a phone has; a pad row for "button A of a controller that may
not be connected" would just be aliases of 确定/软键.

| Android key (code) | MIDP key |
|---|---|
| BUTTON_A (96), BUTTON_R2 (105) | `NJ_KEY_FIRE` |
| BUTTON_B (97), BUTTON_SELECT (109) | `NJ_KEY_SOFT_RIGHT` (cancel) |
| BUTTON_X (98), BUTTON_START (108) | `NJ_KEY_SOFT_LEFT` (menu) |
| BUTTON_Y (99) | `NJ_KEY_GAME_A` |
| BUTTON_L1 (102) | `NJ_KEY_GAME_B` |
| BUTTON_R1 (103) | `NJ_KEY_GAME_C` |
| BUTTON_L2 (104) | `NJ_KEY_GAME_D` |
| DPAD_UP/DOWN/LEFT/RIGHT + axes (moved by the pad driver) | `NJ_KEY_UP/DOWN/LEFT/RIGHT` |

The DPAD codes 19-22 and the fire aliases 23/62/66 were already in `k_keymap`;
the shoulder/trigger/face buttons are the new ones.  Volume keys keep
adjusting media volume and power stays system -- unchanged.

Evidence (status overlay `keys=` column is the cumulative key event count):
`g2-overlay-on.png` keys=6 (world, game menu open), three `input keyevent 96`
(BUTTON_A) -> `g3-overlay-padA3.png` keys=12 and the menu closed, i.e. A fired the menu's "Back to game" button; `input keyevent 109` (SELECT) ->
`g4-padselect-menu.png` keys=14 with the game menu open (soft-right);
unmapped `input keyevent 100` (BUTTON_C) -> `g5-unmapped-c.png`, keys=14
unchanged.

## Mapping table summary

| Android input | MIDP/J2ME effect |
|---|---|
| BACK (4) short | right soft key press to the MIDlet |
| BACK (4) long (550 ms) | port settings panel, game gets nothing |
| MENU (82) | `NJ_KEY_SOFT_LEFT` (unchanged) |
| DPAD (19-22) / MOVED axes | arrows (unchanged) |
| A/B/X/Y, L1/R1/L2/R2, START/SELECT | table above (new) |
| VOLUME_UP/DOWN, POWER | system (unchanged; volume keys also reach the port so its own on-screen volume UI sees them) |
| touch (single pointer) | unchanged; the pad still gives the MIDlet one pointer at a time |

## Audit items (no change needed)

- `setRequestedOrientation(...LANDSCAPE:PORTRAIT)` (GameActivity.java:319) and
  `FLAG_KEEP_SCREEN_ON` (:323) already match the checklist; `dumpsys window`
  reports `mLastWakeLockHoldingWindow=Window{... com.lucinhu.nj2me/.GameActivity}`.
- Multi-touch: `PadPress` tracks up to 16 fingers and lets a movement key and
  jump be held together; only the game pointer is single-touch by design.
- `PadView.releaseAllKeys()` has no caller.  The dialog path relies on the
  framework's ACTION_CANCEL and the emulator does deliver it: a 3 s forward
  hold interrupted by the panel (old r5 APK) did not keep walking after the
  panel closed (`ab-old-2-after.png` vs `ab-old-3-after12.png`, only cloud and
  water animation differs).  Release-on-pause is a separate round-6 change
  (`0f4cf05`-era worktree, not this branch), so nothing here depends on it.

## Non-fixes and open observations

- The panel is still opened by the ≡ handle and by a BACK long press; the panel
  still deliberately does not pause the VM (measured in round 5: 59.6 fps and
  ~33% of one core while it is open).  That is a product decision, documented
  in `docs/notes/2026-11-02-android-lifecycle.md`.
- Touch after resize: at `wm size 480x800` the picture is re-fitted (overlay
  `window=480x800 scale=2.00`) and a tap at (456,20) opens the game's HUD pause
  menu (`h2-480-pausetap.png`), so the touch transform follows the picture.  A
  probe tap at (320,232) intended for the menu's first row instead hit
  "Quit to title" (game logged a save).  Measuring the 320x640 screencap of the
  480x800 display, the four menu rows render at display y ~ 174/254/333/413
  (~80 px apart, i.e. the 2x spacing), not at the 2x-expected
  312/392/472/552: the game's menu is not simply canvas*2 on this display.  This
  is left as an open observation - r5 verified the resize path (HUD icon and
  menu rows reachable), and touching exactly what is on screen still works; a
  dedicated probe is needed before calling it a mapping bug.
- `adb shell input keyevent --longpress` does not hold a key (down+up in one
  frame); use `sendevent` for long-press evidence.
