# FSR1 缩放矩阵、整数倍率与缩小路径实测（2026-11-27）

0.5.51 发布之后的这一轮开发里，开放目标之一，是"把 3×–8× 强力放大、非整数倍率、缩小这三条路径都对着
同帧原生高分真值量化一遍，并量出真实窗口里的呈现开销"。本文记录这轮实测的方法、数据和
结论。实现本身没有因为这次测量而改动：数据支持保持单一立方核 + RCAS 的设计，整数倍率
的指标劣势来自真值与渲染网格的相位关系，而不是核形状。

## 方法

- 真值：`3D版田园物语` 第 1080 帧与 `毁灭战士3` 第 240 帧各自的原生 8× 渲染
  （1920×2560，`.local-tools/debug-runs/hd8-integration/desktop/farm-8x/dump-frames/01080.ppm`
  与 `.local-tools/debug-runs/fsr-quality-round3-3d/doom-8x/dump-frames/00240.ppm`）。
- 参考：把 8× 渲染按精确覆盖面积（逐行的分数覆盖积分）缩小到目标尺寸，即"这个尺寸上
  理想的重采样结果"。
- 源：同样的 8× 渲染按面积缩小到逻辑分辨率 240×320，模拟游戏真正交出来的低分辨率帧。
- 探针：`quality-probe sizes` 直接调用生产代码的 `nj_gles2_present`，每个尺寸单独渲染并
  写回读结果；`sweep-table.py` 计算 RGB MAE、SSIM（8×8 亮度块）与亮度梯度误差。
- 所有数字都是 0–255 的 RGB MAE，越小越好；SSIM 越大越好。

## 整数倍率为什么看起来更差

上表里每个整数倍率都不如它两侧的非整数倍率（3× 比 3.25× 差 39%，4× 比 4.5× 差 26%）。
这不是 RCAS 的问题：纯立方核（模式 6，没有锐化）的同一组数字是 2× 3.718、3× 4.303、
3.25× 3.020、4× 4.509、4.5× 3.648、6× 4.603、8× 4.743，形状完全相同。

四项排查都指向参考而非实现：

1. 换真实 1× 逻辑帧作源（它和面积缩小后的 8× 帧有 MAE 2.010 的固有差异），整数倍率的
   劣势原样出现：480×640 3.537、720×960 4.659、780×1040 3.698、960×1280 4.968、
   1080×1440 4.111、1920×2560 5.121。
2. 与原生 4×/6×/8× 渲染直接对比：960×1280 下 4.251 对 4.255、1440×1920 下 4.331 对
   4.373、1920×2560 下 4.538 对 4.452 —— 面积参考本身是准的，整数档的劣势在指标里真实
   存在。
3. 一维玩具模型（8× 带限随机场景、纹素=8 个样本均值）里误差随倍率平滑上升，只在 4× 略
   高于 4.5×，没有 2D 这样 26–39% 的跳变，说明跳变来自 2D 场景内容与 8× SSAA 渲染网格
   的相位相干，而不是一维重采样数学。
4. 对 FSR1 输出做高斯模糊只能把 960×1280 的误差降低 2.3%、1440×1920 降低 0%，说明非整数
   参考并非"被模糊过"；相反，非整数倍率的面积缩小会混合原生像素、让参考更平滑，因此
   非整数档的分数是偏乐观的，整数档才是更诚实的对照。

对 14 个 A 值（-0.25 … 0.5）做逐倍率扫描：最佳 A 相对 A=0.10 只把 2D MAE 降低 0–1.9%
（2.25× 最好，1.9%），3D 帧 0.0%。为一个几乎看不见的收益引入逐倍率参数不值得，核保持
单一 A=0.10。

## 缩小矩阵（面积路径）

源是原生 1920×2560 渲染，参考是同一渲染的精确面积缩小，因此这里测的是面积路径与理想
面积采样的差距：

| 目标 | MAE | 最大误差 | 完全一致像素 |
| --- | --- | --- | --- |
| 1080×1440 | 0.135 | 162 | 95.00% |
| 960×1280 | 0.119 | 150 | 98.91% |
| 781×1045 | 0.072 | 101 | 95.35% |
| 720×960 | 0.064 | 95 | 99.08% |
| 480×640 | 0.118 | 88 | 98.80% |
| 443×591 | 0.131 | 82 | 95.33% |
| 400×533 | 0.068 | 52 | 96.12% |
| 300×400 | 0.167 | 58 | 86.63% |
| 240×320 | 0.120 | 47 | 97.92% |

MAE 都在 0.07–0.17 之间（不到 0.1% 的量程），差异来自 8 位定点/浮点舍入与多阶段缩小的
二次舍入，路径本身正确。

## 结论

- 放大：单一立方核 A=0.10 + RCAS 在 2×–8× 全区间成立，整数倍率的指标劣势来自参考的
  相位性质，不据此调整实现；逐倍率 A 参数没有采用。
- 缩小：面积路径与理想面积采样等价（MAE ≤ 0.17/255）。
- 桌面真实窗口的呈现开销见 `docs/notes/2026-11-27-fsr-cubic-reconstruction.md` 的
  开销一节；Android 端的呈现开销见下节。
- 测试全部通过：增强版 236/236、软件版 222/222（见各节）。

## Android 呈现开销（模拟器，宿主 GPU）

Android 版直接画到 EGL 窗口并 `eglSwapBuffers`，没有桌面路径的回读，所以桌面的毫秒数
不能直接套用。这一轮给 GLES2 呈现加了可选的逐帧统计：

```sh
adb shell setprop debug.nj2me.present_stats 1
```

属性每秒采样一次（`__system_property_get`，采样结果缓存在堆上的呈现状态里，保持
libnj2me.so 的 .data/.bss 仍为 0 字节）；每 120 帧把绘制（make-current、纹素上传、滤镜
pass）与交换（`eglSwapBuffers`）分别按 min/median/p95 打进 logcat：

```
present stats: mode=5 1080x2400 frames=120 draw ms min=2.82 median=3.68 p95=4.31
present stats: swap ms min=4.61 median=5.89 p95=8.05
```

测量对象：Medium_Phone_API_36.1 AVD（x86_64 APK，`-gpu host`，渲染器是宿主的
RTX 5080 经模拟器转换层），`毁灭战士3`（240×320 逻辑分辨率），窗口 1080×2400，呈现区域
取窗口宽度能容纳的最大整数倍 4×（960×1280），每种模式在预热后统计 3 个窗口：

| 模式 | draw min | draw median | draw p95 | swap median |
| --- | --- | --- | --- | --- |
| 最近邻（mode 0） | 3.00–3.36 | 4.44–5.36 | 5.98–8.09 | 8.36–10.98 |
| 双三次（mode 6，纯立方核） | 3.00–3.21 | 4.22–4.70 | 5.59–8.01 | 7.47–9.96 |
| FSR1（mode 5，立方核 + RCAS） | 2.51–2.82 | 3.68–4.80 | 4.31–8.54 | 5.89–8.75 |
| FSR1，高清渲染 8× 源（1920×2560 → 960×1280 面积采样） | 2.44–2.89 | 3.67–3.91 | 4.67–4.87 | 6.03–6.53 |
| 最近邻，高清渲染 8× 源 | 2.48–2.86 | 3.46–3.85 | 4.51–5.07 | 6.07–6.45 |

读法：三种滤镜在同一尺寸上的差值落在窗口之间的噪声里（中位数波动约 0.9 ms，比滤镜
之间的差异还大），说明在这台模拟器上呈现开销由每帧的纹素上传、窗口提交和转换层固定
成本决定，滤镜 pass 不是瓶颈；这也解释了为什么 4× 放大的 FSR1 不比最近邻贵。8× 高清
源走面积缩小路径，绘制的中位数与 4× 放大相当，上传更大的源（1920×2560）与面积 pass 的
成本被固定开销吸收。桌面/真机的绝对数字会不同，但"滤镜不是呈现瓶颈"的结论与桌面窗口
实测（见立方核说明的开销一节）一致。

限制：这一轮没有可用的物理 Android 设备（`adb devices` 只有模拟器），FSR2 用的
arm64-v8a APK 无法在 x86_64 模拟器上运行，因此 FSR2 路径本轮没有设备内数据；模拟器
的 GPU 是宿主直通+转换层，绝对值不代表手机。

同时完成的设备内回归：设置项持久化（GL 呈现 FSR1、GL 放大 8×、高清渲染倍率 8×）；
FSR1 → 双三次 → 最近邻 → 关闭（软件呈现）热切换后同一 PID 无 EGL 错误；高清渲染 8× 重新
启动后按窗口宽度截断为 4× 呈现且无 EGL/OOM；游戏竖屏锁定，旋转不改变画面；静止标题画面
不重绘时截图逐字节相同（滤镜在下次重绘生效）。
