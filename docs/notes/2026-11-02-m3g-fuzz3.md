## Findings

### 1. `Node.animate()` recursed without a bound through a cyclic Group graph

Repro: a .m3g whose two Groups name each other as children.  The loader links
Group children from raw references and has no ancestor test (Java
`Group.addChild()` refuses that edge), so the graph it hands back can be
cyclic.  The render walks (`collect_walk`, `collect_lights_walk`) stop at
depth 32; `m3g_animate_object()` walked the same graph with no bound and
recursed forever the first time a title animated such a scene.

Pre-fix: `evidence/run2/fuzz7.log` -
`==ERROR: AddressSanitizer: stack-overflow`, hundreds of recursive
`m3g_animate_object` frames.  `evidence/prefix-animate-cycle-test.log` (only
the source fix reverted, tests kept) reproduces it in the unit test: ASan
stack-overflow in the forked probe and
`FAIL animate() on a cyclic group graph terminates`.

Fix: `src/midp/nj_lib_m3g.c` - `m3g_animate_object()` gained a `depth`
parameter and returns at `depth > 32u`, the same bound the render walks use.

Test: `test_m3g.c:test_loader_group_cycle_animate()` builds the cycle the way
a file does (each Group's `_nj_kids` vector names the other; `addChild()` is
not used) and calls `animate(0)` in a forked child.
Check: "animate() on a cyclic group graph terminates".
Post-fix: `evidence/postfix-animate-cycle-test.log`, 881 checks / 0 failures,
no sanitizer output.

### 2. `Loader.load()` returned an array of nulls for a fully-referenced container

JSR 184: load() returns the file's root objects, and "the array is guaranteed
not to contain any null objects".  `nj_m3g_build_objects()` computes roots by
marking referenced objects in `is_ref[]`.  When every object is referenced
(a cycle), `count` falls back to "how many objects exist" - but the fill loop
still skipped every `is_ref`-marked object, so the array was allocated with
the right length and filled with nulls.  The fuzzer's cyclic container was
duly handed back as two nulls (this is also why its stack overflow only
happened once animate() was called: the loader had hidden the groups).

Fix: `src/midp/nj_lib_m3g.c` - a `fallback` flag now remembers that `count`
came from the fallback loop; the fill loop only applies the `is_ref` filter in
the normal case.  The World still goes first.

Test: `test_m3g.c:test_loader_cyclic_roots()` loads the two-Group cyclic file
and requires two non-null Group roots.
Check: "a cyclic .m3g still returns its two Group roots, not nulls".
Pre-fix: `evidence/prefix-animate-cycle-test.log` - `FAIL a cyclic .m3g still
returns its two Group roots, not nulls`.
Post-fix: pass.

### 3. `jr_setup()` read VertexBuffer fields out of a foreign object

A Mesh loaded from a file names its vertex buffer with a raw reference, and
`nj_m3g_link_meshes()` stores whatever that reference resolves to.  A
malformed container can therefore say that the vertex buffer is a Material,
a Camera, a Transform, ...  `jr_setup()` then read VertexBuffer field offsets
in that object and treated a foreign int/ref field as the `_nj_positions`
VertexArray reference, feeding it to `nj_array_data()`.  UBSan reported
"member access within misaligned address 0x000000050001 for type 'struct
nj_object'" and ASan reported a SEGV in `nj_field_read_ref`
(`evidence/run3/fuzz8.log`).

Fix: `src/midp/nj_lib_m3g.c` - `jr_setup()` refuses a non-null `vb` whose class
is not `VertexBuffer` and returns 0 (draw nothing), matching JSR 184's
"a scene that cannot be drawn draws nothing" contract.  A mesh built through
the Java API always has a VertexBuffer, so valid scenes are unaffected.

Test: `test_m3g.c:test_mesh_foreign_vertex_buffer()` builds a normal Mesh,
overwrites its `_nj_vb` with a Material (what a malformed file does), puts it
in a World and calls `Graphics3D.render(World)`.
Check: "a mesh whose vertex buffer is not a VertexBuffer draws nothing,
without faulting".
Pre-fix: `evidence/prefix-vb-class-test.log` - `ERROR: AddressSanitizer: SEGV`
in `nj_field_read_ref` called from `jr_setup`, 881 checks / 1 failure.
Post-fix: `evidence/postfix-vb-class-test.log`, 881 / 0, no sanitizer output.

## Investigated, not changed

* `Object3D.release()` is not implemented by the runtime (absent from the
  Object3D method list, native table and the generated stubs), so a title
  calling it gets NoSuchMethodError.  It is not a memory-safety hole and
  adding API surface is out of scope for this round; noted for the API-gap
  list.
* The same "file reference names a foreign object" pattern applies to
  `Mesh._nj_ib`/`_nj_app`.  The index-buffer path already looks fields up by
  the object's own class name (so a foreign object yields no fields rather
  than wrong offsets); the appearance path still reads `Appearance` offsets
  from whatever the reference names.  No crash was reached in the bounded
  runs, so no speculative change was made; it is the same class of bug as
  finding 3 and is worth hardening if a repro shows up.
* Java arrays live inside the VM's `nj_heap` arena, so ASan cannot see
  intra-arena over-reads.  Findings here are UBSan diagnostics, ASan SEGVs
  at the arena boundary and API-contract violations.
