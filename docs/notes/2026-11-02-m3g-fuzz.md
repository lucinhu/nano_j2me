# M3G / FileConnection fuzz round (2026-11-02)

Task: shared task-11. Base: `b18d0a2`, branch `r3-bugs`. Desktop only.

## Goal

Hammer the JSR-184 (M3G) and JSR-75 (FileConnection) natives with edge-case
arguments under ASan + UBSan, looking for real memory-safety bugs: crashes,
out-of-bounds access, undefined behaviour, hangs. Expected API exceptions
(IllegalArgumentException, IndexOutOfBoundsException, ConnectionClosedException,
...) are normal and are caught by the driver.

## Finding: Graphics3D.setLight(Integer.MAX_VALUE) overflowed a size computation

`NJFN(m3g_g3d_setLight)` in `src/midp/nj_lib_m3g.c` accepted any non-negative
index and grew the Java-side light array to that index. The matrix table size
was then computed while the `index + 1` was still a signed `int`:

    count = (nj_u4)(index + 1) * NJ_MF;

For `index = 0x7FFFFFFF`, `index + 1` overflows (undefined behaviour). The
pre-fix run reproduced it immediately:

    src/midp/nj_lib_m3g.c:14128:37: runtime error: signed integer overflow:
    2147483647 + 1 cannot be represented in type 'int'

The call then threw `OutOfMemoryError` from the oversized allocation instead
of refusing the index. A crafted or corrupted light index (a title can pass an
arbitrary int, and loaded scenes carry indices too) therefore reached UB and a
multi-gigabyte allocation request; the documented API answer for an
out-of-range index is `IndexOutOfBoundsException`.

The renderer and its per-draw tables are `NJ_M3G_LIGHTS` (16) entries wide, so
an index past the last one can never be lit. The fix rejects it up front:

    if (index >= NJ_M3G_LIGHTS) {
        NJ_THROW(vm, "java/lang/IndexOutOfBoundsException", "light index");
    }

## Findings from the follow-up "grow to caller index" audit

The same shape - a Java-visible integer sizing an array or a loop - was
audited across every native that takes an index or a count. Two more hits were
reachable from Java without privileged state and are fixed in the same commit:

1. `NJFN(m3g_mesh_setAppearance)`: when the appearance Vector was shorter
   than the requested index, the code grew it in a loop up to
   `index + 1` with no upper bound (and, on int wrap-around, an infinite
   condition). `Mesh.setAppearance(1, appearance)` on a one-submesh mesh
   silently created a second submesh instead of throwing, and
   `setAppearance(0x7FFFFFFF, ...)` asked for a two-billion element
   `java.util.Vector` (OOME at best). A Mesh's submesh count is fixed at
   construction, so the index is now rejected up front with
   `IndexOutOfBoundsException` ("invalid submesh"); the lazy single-submesh
   path (`count == 0`, index 0) keeps working.
2. `NJFN(m3g_g3d_getLight)`: the bound was the Java array's length, which has
   slack past the configured lights and keeps its slots after
   `resetLights()`. `getLight(16)` after `setLight(15)` returned `null`
   without throwing, and `getLight(0)` after `resetLights()` returned a stale
   light; both now raise `IndexOutOfBoundsException` from the light count
   (`_nj_nlights`), as the API contract asks.

Audited and clean (no unbounded growth, or growth guarded): SkinnedMesh
`addTransform` doubled bone arrays with a `want > 0x7fffffff` overflow guard;
`m3g_g3d_slot` only serves setLight, now bounded to `NJ_M3G_LIGHTS`;
`VertexArray.set/get` and `img2d_set` use 64-bit products (round-1 fixes);
`KeyframeSequence` sizes from `nkeys * ncomp` only after a `times` allocation
that fails first for huge `nkeys`; `MorphingMesh.getMorphTarget`,
`getIndexBuffer`, `getAppearance`, `getChild`, keyframe get/set and texture
unit indices bound-check their arrays. `Transform.transform(VertexArray)`
still loops the stored vertex count (a huge `numVertices` from the
constructor makes it slow, not unsafe); noted, not changed.

## What was probed and found clean

Wave 2 exercised: extreme viewports (including INT_MAX and -0x40000000 sizes,
clipped against the target by `m3g_target_bounds`), NaN/Inf vertex and matrix
data in immediate and retained rendering, all visible light slots and beyond,
array transforms with short destinations, keyframe/animation extremes,
SkinnedMesh/MorphingMesh bone and weight APIs, FileConnection edit paths under
READ/WRITE/READ_WRITE mode, and RMS odd IDs. No ASan or UBSan diagnostic
besides the light-index overflow above; no hang within the frame budget.

Caveat from the round-1 report still applies: Java arrays live inside the VM's
`nj_heap` arena, so ASan cannot see an out-of-bounds access that stays inside
that arena; the API-level checks are what catch those.
