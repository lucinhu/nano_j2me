# x86-64 backend for the bounded JIT: implementation and measured ceiling

Date: 2026-11-02 (round 6, task-17). Worktree `r6-jit`, base main `dfd6522`.
The bounded JIT (`src/core/nj_jit.c`) had backends for RV32 and ARM64 only, so
its ceiling was unmeasurable on this host and on the x86-64 Android emulator.
This change adds a system-V x86-64 backend that mirrors the ARM64 opcode
coverage and the existing exits/faults protocol, plus an execution test and the
build/CMake wiring.

## What was added

- `src/core/nj_jit_x86_64.c` (~1500 lines): emitter for the same opcode set as
  the ARM64 backend, using the ARM64 decoder/scan code as the structural model.
  Register ABI: `rdi` = incoming operand stack, `rsi` = locals, `edx` = budget,
  `eax` = result word; `r10d` carries the completed-bytecode counter only for
  blocks with taken branches. Calls are caller-saved only; no C calls, no
  allocation, no frame changes inside emitted code.
  - Straight-line windows, internal forward jumps, forward exits, and bounded
    back edges with the quantum-budget check at the loop entry.
  - Fault exits for: null receivers/arrays, wrong array kind, out-of-bounds
    array access, `.class`-level checks on `getfield`/`putfield`, and `idiv`/
    `irem` with divisor 0 or -1 (x86 `idiv` would trap on `INT_MIN / -1` where
    Java wraps, so both cases exit to the interpreter before any side effect).
  - Int/float/double arithmetic except long arithmetic, `iinc`, `ineg`,
    `i2b/i2c/i2s`, `dup/dup2/swap/pop/nop`, `arraylength`, `iload..aload` and
    `istore..astore` (wide zeroing of the high slot), `getfield`/`putfield`,
    `iaload`/`iastore`, `if*`/`goto`, and `fadd/fsub/fmul/fdiv` +
    `dadd/dsub/dmul/ddiv`, `fneg`/`dneg`.
  - Everything else is declined (invokes, `new*`, statics, wide-array ops,
    long arithmetic, switches, monitors, returns, ...), which ends the block.
- `include/nj2me/nj_config.h`: `NJ_JIT_HOST_X86_64` detection (x86-64, LP64,
  little-endian) and it joins `NJ_JIT_HOST_SUPPORTED`.
- `src/core/nj_jit_internal.h`, `src/core/nj_jit.c`: declarations and the
  `x86_64-baseline` backend selection (`NJ_JIT_ENGINE_NAME`).
- `CMakeLists.txt`: backend source in `NJ_SOURCES`; `tests/test_jit_x86_64.c`
  added next to `test_jit_arm64`. `tests/embedded/idf/components/nj2me/CMakeLists.txt`
  lists the new file (the embedded port build gate requires the source list to
  be complete).
- `tests/test_jit_x86_64.c` (~700 lines): analyze/compile metadata agreement
  (including capacity prefixes and no writes past capacity), and real native
  execution of arithmetic, loops/budget exits, division faults (0 and -1),
  `i2b/i2c/i2s`, `swap`, float add/neg, a fake-VM `getfield`/`putfield`
  fixture, int-array load/store/bounds fault, and `arraylength`.
  Run: `build-jit/test_jit_x86_64` -> 4416 assertions, 19 blocks compiled,
  21 native executions, PASS.

JIT remains opt-in: the default build still compiles the interpreter only.
`cmake -S . -B build-jit -G Ninja -DCMAKE_BUILD_TYPE=Release -DNJ_ENABLE_JIT=1`
selects the backend. `NJ_JIT_HOT_THRESHOLD` / `NJ_JIT_MIN_BLOCK_INSNS` remain
the tuning knobs.

## Coverage on the real workload

`NJ_JIT_STATS=1` prints one `jit:` line from the runner (temporary diagnostic,
not part of the commit). Minecraft fresh-world creation, uncapped, 6000 frames:

- `compiled=1,258,771`, `executed_blocks=697,379,280`,
  `bytecodes=7.305e9` natively executed, `declined=2,578,010`,
  `unsupported=1,673,443`, `short=904,567`, `faults=0`,
  `code_bytes=14.5 KB` requested, `peak_code_bytes=20.7 KB`.
- Average native block: 7.305e9 / 697e6 = 10.5 bytecodes.
- Interpreter-retired bytecodes in the same run: 15.35e9 (the JIT build
  disables the round-3 superinstruction fusions for the interpreter, so this
  count is not directly comparable to the interpreter build's 9.99e9).
  Native share of `native + interpreter` counted bytecodes is about 32%.
- `bench.jar`: 78.4e6 native bytecodes of 112.1e6 counted -> about 41% native,
  average native block ~5.4 bytecodes (53 compiled blocks).

## Performance: JIT-on vs interpreter (desktop, x86-64, CPU pinned)

Minecraft fresh-world replay, uncapped (`--fps 0`), 6000 frames, same keys
script, fresh `--fs-dir` per run; game-reported timers:

| build | GEN ms | world blocks | GEN ms/1K blocks | save ms | prepare ms | total wall s |
| --- | --- | --- | --- | --- | --- | --- |
| interpreter (default) | 13102 | 1443K | 9.08 | 2712 | 3382 | 33.1 |
| JIT default (hot=8, min=4) | 20807 | 1486K | 14.00 | 2933 | 5061 | 44.4 |
| JIT tuned (hot=64, min=8) | 17406 | 1607K | 10.83 | 3016 | 4670 | 45.3 |

`tools/bench.sh 5` fixed-workload CPU time (min of 5, `taskset -c 21`):
interpreter 0.176-0.177 s; JIT default 0.278-0.279 s (+57%); JIT tuned
(hot=64) 0.334 s.

So the current JIT is a clear regression: +59% generation time, +34% total
wall time for world creation, and +57% on the fixed benchmark. Raising the
compile threshold recovers about a quarter of the generation cost but does not
change the verdict.

### clang -Os desktop (target-like codegen)

Same replay and bench, clang 23.1.4 with `-DCMAKE_C_FLAGS_RELEASE=-Os`
(`build-clang` = interpreter, `build-clang-jit` = JIT):

| build | GEN ms | world blocks | GEN ms/1K blocks | save ms | prepare ms | total wall s |
| --- | --- | --- | --- | --- | --- | --- |
| clang -Os interpreter | 14212 | 1593K | 8.92 | 3035 | 3631 | 38.2 |
| clang -Os JIT default | 23641 | 1473K | 16.05 | 3526 | 5387 | 40.0 |

`tools/bench.sh 5` min CPU: interpreter 0.192 s, JIT 0.292 s (+52%). The
verdict is the same on the target-like compiler: JIT-on costs about +80% per
1000 generated blocks (+66% raw GEN), +48% on the load-back prepare and +16%
on the save, so the block-granularity ceiling is not a gcc artifact.

## Why, and what it means for finishing ARM64

The block granularity is the problem, not the encoding:

- The interpreter after round-3 fusion runs at about 2.8 ns per bytecode
  (~8-9 cycles). A native block costs a C call boundary plus the
  `jit_guard`/ticket bookkeeping per entry/exit (~15-20 ns). With an average
  block of 5-10 bytecodes, the call/exit overhead is larger than the
  dispatch it replaces.
- 697 million block entries for 6000 frames is ~116k calls/s of pure
  boundary overhead; `unsupported` probes (1.67M declines) and
  `short` declines (0.90M) add more work on the interpreted fallback.
- The JIT build disables the superinstruction fusions (`NJ_FUSION_ALLOWED`),
  so the code that stays interpreted runs slower than in the interpreter
  build. For Minecraft's small methods, a large share of bytecodes stay
  interpreted.
- The 13 KB requested code footprint and 20 KB peak show that hot methods are
  composed of many tiny blocks; there is no cross-block chaining, so a loop
  body that fuses well in the interpreter becomes 3-5 native blocks with a C
  return between each.

Verdict: completing the ARM64 backend as-is is **not worth it for user-facing
performance**. ARM64 would have the same structural ceiling: same block
selection, same C boundary, same fusion shutdown. The ceiling is set by
block size and entry cost, not by the ISA. The JIT only becomes interesting
if the framework changes, in one of these directions (in rough order of
value):

1. Compile the fused interpreter sequences (round-3 superinstructions) as a
   single native block unit, so block size grows without adding analysis
   coverage.
2. Reduce entry cost: batch several hot blocks per C call (chaining/continuation
   in emitted code) or let the interpreter dispatch directly into a block
   without the probe/ticket path for hot sites.
3. Do not disable the interpreter fusions when JIT is enabled (they help the
   interpreted remainder).
4. Only compile blocks longer than a higher effective threshold (the tuned
   run suggests the optimum is not at the current defaults; the fixed bench
   stays colder than the threshold, so this also needs a workload-aware
   policy).

Until one of those is done, the interpreter plus fusions is the better
machine for Minecraft on x86-64.
