# 整数索引运算与数组读取尾融合：筛选结果

本轮候选未合入。固定种子世界生成的首次筛选中，候选减少了指令分派，
但没有达到预先设定的 CPU 时间减少 3% 门槛，解释器代码体积反而增加。
以下是单对筛选记录，不是稳定回退幅度、Android 帧率或加载速度结论。

## 候选和语义边界

基线为 `78114ba5493dce28776e6fd0beae26d8a96ac63a`。仅在隔离副本的
`NJ_CONST_ARITH_FUSE` 和 `NJ_ILOAD_CONST_ARITH_FUSE` 中，在整数运算成功后，
识别紧随其后的 `0x2e` 至 `0x35` 数组读取指令：先保存计算出的索引，
弹出索引槽，再复用现有 `NJ_ARRAY_LOAD_BODY`。没有按游戏类名识别热点。

现有数组加载体处理全部八种读取、boolean 归一化、带符号 byte/short、
无符号 char，以及 long/double 的双槽结果。复用时必须维持算术异常先于
后续数组访问、数组 null 检查先于越界、异常 PC 指向原数组指令等约束。
现有融合开关、JIT 门控和字节码长度判断保持原样。

只读审查还发现，去掉数组指令的 fetch 边界可能跳过已有的栈上限拒绝。
现有 `NJ_FETCH_OP` 在 `sp > stack_limit` 时抛出 VerifyError；若先弹出索引，
就可能隐藏非法的临时栈高度。因此，唯一实际构建和测量的候选在弹出索引前
使用 `sp <= stack_limit` 门控。超限时走原分派，不吞掉原检查。
这项保护已在首次构建前加入，没有测量无保护版本。

源码入口见 [nj_interp.c](../../src/core/nj_interp.c) 的上述宏和
`NJ_FETCH_OP`，原回归 oracle 见
[check_superinstr_digest.sh](../../tools/check_superinstr_digest.sh)。
现有 oracle 的 26 类摘要并不专门证明新增的“索引算术 → 数组读取”边界。
候选未被选中，因此本轮没有增加或执行新的融合回归矩阵。

## 构建和固定工作量

使用 x86-64、GCC 16.2.1、Release `-O3`、threaded dispatch、superinstructions
开启、JIT 关闭。基线和候选从实际 Ninja 命令提取相同编译链接参数，使用同一
冻结库和 [bench_minecraft_gen.c](../../tools/bench_minecraft_gen.c)。
重新构建的基线解释器 `.text` 与归档对象逐字节一致。

原版 `MinecraftJ2ME_PE_0.6.1_V2.2.jar` 的 SHA-256 为
`fbe72c5c5cdd3042daa69475bdcbd50f7d0e85afcbd699caf3b1f627e014bcd6`。
固定种子为 12345，绑定 CPU 0，先基线、后候选各运行一次。
计时范围是 `Gen.generate()`，不包括菜单、磁盘存档或画面渲染。

## 决定与后续条件

候选未通过首对门槛，因此停止，没有追加三对确认、LOAD 筛选或 Android
测试。此次较慢的单次结果也不足以断言它在所有机器上稳定变慢。
代码膨胀和分派减少是已测事实；没有 PMU 或 cache-miss 证据，不能把耗时变化
直接归因为指令缓存。更少分派本身不能作为上线理由。

若以后以不同代码布局重新尝试，需要重新构建、重新筛选，不能复用本次
结果作为性能证明。候选被选中后，才需完成八种数组读取、双槽结果、异常 PC、
null/越界/算术异常优先级、非法 max_stack 回退、branch-to-middle、
portable/threaded、融合开关与 JIT 门控的针对性验证。

本轮只保留实验结论。当前运行时代码沿用已通过 155 项回归的基线；
本轮未重跑该套件，也没有将其计作候选的验证结果。
有关已确认的 GEN/LOAD 热点，见
[J2ME-Loader 对照](2026-11-10-j2me-loader-comparison.md) 和
[实际 LOAD 分段采样](2026-11-10-minecraft-load-profile.md)。
